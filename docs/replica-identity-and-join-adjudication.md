# replica 정체성과 join — 산정

**이것은 스펙이 아니다.** `docs/design/0000`–`0003`이 스펙이고, 이 문서는 *스펙에 무엇이
필요한지*를 재는 산정이다. 그래서 `docs/design/` 밖에 있고 번호도 붙이지 않는다. 이 문서의
어떤 문장도 계약이 아니며, **MUST / MUST NOT을 쓰지 않는다** — 인용 안에 있는 것은 인용된
문서의 계약이다.

### 0.5 오늘 문서 실측 — replica·join·포크를 규정하는 절은 여전히 0건

`docs/design/` 네 문서에서 `replica`·`source id`·`join`·`fork`·`포크`·`사본`을 훑었다. 걸린 8건은
**전부 다른 맥락**이고, replica 정체성·join·포크 감지를 규정하는 절은 **0건**이다.

| 위치 | 무엇 | 이 산정과의 관계 |
|---|---|---|
| `0001:41` | *"구독 중인 replica에 밀어준다"* | SSE 수신자로서의 replica. 정체성 규정이 아니다 |
| `0001:80`, `0002:548`, `0003:1117` | 악의적 **fork**가 hub 주소를 바꾸는 것에 대한 방어 | 리포 fork이지 replica 포크가 아니다. 게다가 2안 결정으로 *"커밋되는 정체성 파일"* 전제 자체가 소멸한 자리다 |
| `0001:114` | *"신규 replica 부트스트랩"* 의 콜드 스타트 비용 | 성능 서술 |
| `0000:151` | read surface epic (headless replica…) | 전신 유산의 처분표 |
| `0002:194` | *"먼저 저장돼 있던 **사본**의 커서"* | dedup의 사본이지 replica가 아니다 |
| `0003:232` | *"같은 이름의 두 프로젝트, fork, origin 변경"* | 클라이언트 mint id가 모호해지는 예시 |

`0003` 전체에 **`replica`라는 낱말이 한 번도 나오지 않는다.** 제어 평면이 아는 주체는 *주체
(subject)* 와 *작업공간(workspace)* 둘뿐이다 (`0003:79-85`, `§4`).

## Q1 — P2(a)의 출처 축은 어디에 실릴 수 있는가

### Q1.0 먼저 확인해야 할 것 — "선별 제거"는 오늘 어느 후보에서도 불가능하다

후보를 재기 전에, **네 후보 전부에 공통으로 걸리는 벽**이 있다. 이것을 먼저 적지 않으면 아래 표의
"서버가 선별 제거 가능한가" 칸이 전부 같은 이유로 `아니오`가 되는 것이 후보의 차이처럼 보인다.

`0002-transport-spec.md:110-111` (§1.4):

> 로그는 **append-only**다. 수용된 이벤트는 **수정되지도 삭제되지도 않는다** (MUST NOT).
> "retract"는 payload 안의 클라이언트 개념이지 전송 평면의 동작이 아니다.

그리고 `0002:535-538` (§8 미결 6)이 보존(retention)을 열어 둔 채로 남겼고, `0003:1094-1096`
(§8 미결 4)이 **로그 단위 삭제조차 없다**고 적었다 — *"§2에 로그를 만드는 경로만 있고 없애는
경로가 없다."*

**따라서 "replica X가 기간 Y에 쓴 것을 선별 제거"의 문자 그대로의 실행 — 그 이벤트들을 로그에서
없애는 것 — 은 출처 축을 어디에 싣든 오늘의 계약에서 불가능하다.** 출처 축이 답할 수 있는 것은
그 앞 단계, **선별 식별**(그 집합을 정확히 특정하는 것)까지다. 아래 표의 "서버가 선별 제거
가능한가" 칸은 그러므로 실질적으로 **"서버가 그 집합을 특정할 수 있는가 + 특정한 뒤 무엇을 할 수
있는가"** 를 잰다.

이 구분이 결론을 바꾼다. **P2(a)를 만족시키려면 조각이 둘 필요하다** — 출처 축을 세우는 것과,
그 위에서 "되돌림"이 무엇을 뜻하는지 정하는 것(§1.4 삭제 금지·§8-6 보존과 함께). §Q5가 그렇게
자른다.

### Q1.2 후보 (가) — `payload` 안: 선별 제거의 주체가 없다

**절차.** join을 되돌리려는 사람은 서버에 아무것도 시킬 수 없으므로, **각 소비자가 각자 되돌린다.**
소비자는 `GET /v1/logs/{logId}/events`를 `hasMore: false`가 될 때까지 돌려 전량을 받고
(`0002:302-303`), 각 이벤트의 `payload`를 자기 스키마로 파싱해 `source == X` 이고 타임스탬프가
기간 Y 안인 것을 자기 로컬 뷰에서 제외한다. 서버의 로그는 한 바이트도 바뀌지 않고, pull·subscribe는
그 이벤트를 계속 실어 보낸다.

**왜 이것이 P2(a)를 만족하지 못하는가.** 01:52 결정은 join을 *"되돌릴 수 있는 **사건**"* 으로
만들라고 적었다. 사건은 한 번 일어나고 모두에게 같은 효력을 갖는 것인데, 이 절차에는 그 사건을
일으킬 주체가 없다 — **되돌림이 소비자 수만큼 존재하고, 하나라도 안 하면 그 소비자에게는
오귀속이 남는다.** 그리고 2안 결정의 요지가 *"정체성의 정본은 hub"* 인데, 이 후보는 되돌림의
정본을 hub 밖으로 내보낸다. 결정의 방향과 반대다.

**부수 효과 하나.** 이 후보는 `0002:522-526`(§8 미결 3, 같은 id·다른 바이트)을 악화시킨다.
출처가 payload 안에 있으면 **출처가 다른 두 이벤트가 같은 `id`를 가질 수 있고**, 그때
first-write-wins(`0002:196`)가 나중 것을 조용히 버린다 — 버려진 쪽의 출처는 payload 안에 있었으므로
서버는 자기가 무엇을 버렸는지 영원히 모른다.

### Q1.3 후보 (나) — 봉투 필드: 불변식 1을 깨고, 깬 값을 못 받는다

**절차.** 봉투가 `{id, payload, source}`가 되면 스토어에 `source` 컬럼이 서고, 서버는
`DELETE FROM events WHERE log_id=? AND source=? AND seq BETWEEN ? AND ?`를 **쓸 수 있는 모양**이
된다. 그런데 그 `DELETE`는 `0002:110`이 MUST NOT으로 금지한 것이므로, 실제로 실행할 수 있는 것은
읽기 경로에서의 제외 — `readPage`의 `WHERE`에 `AND source != ?`를 더하는 것 — 뿐이다. 그것은 제거가
아니라 필터이고, 필터가 걸린 순간 `0002:317-321`(미지 커서 → 전량 반환, 조용한 누락 금지)이 세운
*"서버는 과잉 전달하거나 명시적으로 갭을 알린다"* 는 관통 규칙과 부딪힌다 — 필터에 걸려 빠진
이벤트는 **조용한 누락**이다.

**깨는 대가를 `0002:452-457` 표의 다른 행들과 함께 재면:**

| 불변식 | (나)가 미치는 영향 |
|---|---|
| **1. 불투명 페이로드** | **직접 깬다.** `0002:454`가 표현 근거로 든 것 중 *"봉투가 `id`+`payload`뿐"* 이 사실이 아니게 된다. 나머지 근거(payload 해석 금지·바이트 보존·prefix-blind)는 남으므로 행 전체가 `아니오`가 되는 것은 아니지만, **`예`로 남길 수는 없다** |
| **2. id 기준 멱등 dedup** | **간접적으로 흔든다.** dedup 키가 `(log_id, event_id)`(`src/store.ts:252`)인 채로 봉투에 `source`가 생기면, *"같은 id·다른 source"* 라는 상태가 표현 가능해지는데 dedup은 그것을 그냥 `duplicate`로 접는다. 키를 `(log_id, source, event_id)`로 넓히면 `0002:265-271`(§2.4 재시도)이 깨진다 — 재발급으로 source가 바뀐 replica의 재시도가 **중복 기록**이 된다 |
| **3. append-only + 순서 보존** | 직접 영향 없음. 다만 위의 "읽기 필터"를 얹으면 §3.2의 관통 규칙과 부딪힌다 (위 문단) |
| **4. 두 평면 경계** | **흔든다.** 출처는 *"누가 썼는가"* 이고 그것은 정의상 제어 평면의 어휘다 (`0003:79-85`). 봉투에 실으면 전송 평면이 그 어휘를 알게 된다 |

**그리고 깬 값을 받지 못한다.** 봉투 필드는 **클라이언트가 채우는 값**이다. 샌드박스 안의
에이전트가 자기 `source`를 스스로 신고하는 구조이고, 그것은 `0001:76-77`이 못박은 것과 정면으로
어긋난다 — *"신뢰 결정은 샌드박스 밖에 있어야 한다. 안에 있는 에이전트가 자기 권한을 스스로 정할
수 있으면 그건 통제가 아니다."* **오귀속을 고치려고 만든 축이 사칭 가능하면 그 축으로 한 되돌림도
사칭 가능하다.** 신뢰할 수 있게 만들려면 서버가 값을 토큰에서 유도해야 하는데, 그 순간 그것은
봉투 필드가 아니라 서버 파생 컬럼이다 — 그게 후보 (라)다.

### Q1.4 후보 (다) — 통제 평면의 별도 표면: 절반은 이미 서 있다

**절차.** 되돌리려는 사람이 제어 평면에 *"작업공간 W의 기여를 무효로 한다"* 를 기록한다. 소비자는
그 기록을 조회해 무효 집합을 얻고… **여기서 끊긴다.** 무효 집합은 작업공간 단위인데, 소비자가 든
것은 이벤트이고, **작업공간과 이벤트를 잇는 다리가 어느 문서에도 없다.** `0003:35-37`이 제어
평면에게 이벤트를 보는 것을 금지했으므로 제어 평면이 그 다리를 놓을 수 없고, 전송 평면은 작업공간을
모른다 (`src/server.ts:118-124`의 `handleAppend`가 검증된 토큰을 인자로 받지 않는다 — Q1.5).

**그런데 절반은 이미 서 있다.** *"기간 Y"* 의 정본을 제어 평면이 이미 들고 있다:

```ts
type WorkspaceRecord = {            // 0003:880-889
  workspaceId: string
  state: "active" | "closed_flushed" | "closed_discarded" | "revoked" | "abandoned"
  logs: string[]            // 개시 시 스코프
  openedAt: string          // RFC 3339 UTC
  lastHeartbeatAt: string
  endedAt?: string          // 종단 상태에서만
  supersedes?: string
  supersededBy?: string
}
```

`openedAt`·`endedAt`이 기간이고 `logs`가 대상 로그다. **빠진 것은 두 가지뿐이다: (1) replica 축
자체 — 작업공간은 replica가 아니다(§Q1.6), (2) 이벤트를 그 축으로 되짚는 다리.** (다)는 틀린
후보가 아니라 **혼자서는 완결되지 않는 후보**이고, (라)가 정확히 그 다리다.

### Q1.5 후보 (라) — 서버 파생 출처 컬럼 (이 산정이 찾은 것)

**착상은 실측에서 나왔다.** 전송 평면은 **요청마다 검증된 토큰을 이미 손에 쥐고 있고, 그것을 쓰고
버린다.**

```
src/server.ts:554   const result = verifyTransportRequest(toRawRequest(req), options.keys, gateOptions)
src/server.ts:560-563   if (result.request.route === 'append') { … await handleAppend(options.store, broker, result.request.logId, rawBody, res) }
src/server.ts:118-124   async function handleAppend(store, broker, logId, rawBody, res)   ← 토큰이 인자에 없다
```

그 토큰이 싣는 것은 `src/token.ts:98-105`이고 `0003:280-288`의 클레임 표 그대로다:

```ts
export type WorkspaceTokenClaims = {
  readonly tokenId: string
  readonly workspaceId: string
  readonly audience: string
  readonly issuedAt: string
  readonly expiresAt: string
  readonly scope: readonly string[]
}
```

**절차.** `handleAppend`가 검증된 토큰을 함께 받고, `store.append`가 `workspaceId`(그리고/또는
`tokenId`)를 `events` 행에 **서버 스스로** 적는다. 되돌리려는 사람은 제어 평면에서 무효로 할
작업공간 집합을 얻고(`GET /v1/workspaces` — `0003:866-896`), 서버는
`WHERE log_id=? AND workspace_id IN (…)`로 그 집합을 **정확히 특정한다.** 특정한 뒤에 할 수 있는
일은 Q1.0의 벽에 걸리므로 §Q5 S5가 받는다.

**왜 불변식 1을 깨지 않는가.** `0002:91-101`이 금지한 것 셋을 하나씩 대조하면:

- *"서버가 요구하는 필드는 `id` 하나뿐"* — 요구하는 필드가 늘지 않는다. 클라이언트는 여전히
  `{id, payload}`만 보낸다.
- *"서버는 `payload` 안에 필드를 추가하지 않는다"* — payload를 건드리지 않는다.
- *"바이트 보존"* (`0002:96-101`) — 그대로다. `src/store.ts:564-573`의 `encodePayload`가
  받은 슬라이스를 그대로 넣고 `toPullEvent`(`:332-343`)가 그대로 꺼낸다.

그리고 `0002:94-95`가 이 자리를 **명시적으로 열어 뒀다**: *"서버가 붙이는 것(커서)은 봉투 바깥에만
붙는다."* 커서가 이미 그런 값이다 — 서버가 만들고, 봉투에 없고, 응답에 나란히 실린다.

**왜 사칭 불가인가.** 값이 클라이언트 입력이 아니라 **런처가 샌드박스 밖에서 발급받은 토큰의
클레임**이다 (`0003:75` — 제어 평면의 모든 라우트는 런처 자격증명을 요구한다). 샌드박스 안의
에이전트가 바꿀 수 있는 것이 아니므로 `0001:76-77`을 지킨다.

**대가 둘.** ① `workspaceId`는 replica가 **아니다**(§Q1.6). ② 노출 여부가 별개의 결정이다:

- **(라1) 기록만 하고 노출하지 않는다** — pull·subscribe 응답 스키마가 그대로이고,
  `#29`·`#30`의 계약이 **0건** 바뀐다. 되돌림은 서버가 자기 안에서 계산한다.
- **(라2) pull·subscribe 응답에도 싣는다** — `0002:290-295`의 `PullResponse.events[]`에 이미
  `cursor`가 서버 파생 필드로 있으므로 형태상 새로운 종류는 아니지만, `#29`·`#30`의 응답 스키마와
  `sse.ts`의 프레임이 바뀐다.

**(라1)이 보수적이고 되돌리기 쉽다.** 나중에 (라2)로 넓히는 것은 필드 추가이고, 반대 방향은 이미
나간 필드를 거두는 것이라 훨씬 비싸다.

### Q1.6 네 후보 공통 — workspace는 replica가 아니다

**어느 후보를 골라도 `workspaceId`만으로는 "replica X"를 답하지 못한다.**

| 축 | 수명 | 근거 |
|---|---|---|
| **workspace** | 수 분 ~ 수십 분 | `0003:523-524` — *"작업공간은 수 분에서 수십 분 사는 임시 실행 단위이고, 15분은 그 수명과 같은 자릿수다"* |
| **replica** | 클론이 사는 동안 | 01:52 결정 — *"replica id는 config가 아니라 **state**"*, `cp -r`·worktree 상속으로 복사되는 것 |

한 replica가 수십 개의 workspace를 연다. 그러므로 (라)가 특정할 수 있는 것은 *"workspace W가 쓴 것"*
까지이고, *"replica X가 쓴 것"* 은 **replica → workspace 다중 매핑을 누군가 들고 있어야** 나온다.
그 자리는 제어 평면이다 — `POST /v1/workspaces`(`0003:683-686`)의 요청이 replica를 신고하거나,
join이 replica를 등록해 두는 형태다. 즉 **(라)와 (다)는 경쟁 후보가 아니라 한 해법의 두 조각이다.**

### Q1.7 Q1 결론

- **(나)는 만족시킬 수 있으나 불변식 1을 깨고, 깬 값이 사칭 가능해 되돌림 자체가 신뢰를 얻지 못한다.**
- **(다)+(라)의 조합만이 불변식 1을 지키면서 출처를 사칭 불가능하게 남긴다.** (라)가 이벤트에
  workspace 축을 남기고, (다)가 workspace를 replica로 접는다.
- **어느 조합이든 "선별 제거"는 별도 조각이다** — `0002:110`(삭제 금지)과 `0002:535-538`(보존 미결),
  `0003:1094-1096`(로그 삭제 없음)이 함께 열려야 한다.

## Q2 — P3의 포크 감지가 `#27` 위에 설 수 있는가

### Q2.1 판정

> 결정이 적은 전제 **"UNIQUE + 커서가 이 감지의 부품을 이미 제공한다"** 는 — **거짓이다.**

유보 없이 적는다. UNIQUE는 감지의 부품이 아니라 **P3가 만드는 피해의 통로**이고(§Q2.4-5),
커서는 감지가 요구하는 종류의 상태가 아니다(§Q2.3). 다만 결정이 가리킨 방향 자체가 틀린 것은
아니다 — **커서를 쓰지 않는 다른 감지 경로가 있고**, 그것도 이 절이 적는다(§Q2.6).

### Q2.2 `#27`의 계약 — 이슈 본문·`#15` 결정, 그리고 머지된 실물

#31이 요구한 대로 이슈 본문과 `#15` 결정에서 옮겨 적고, §0.3에 따라 **실물을 나란히 둔다.**

**(a) `UNIQUE(log_id, event_id)`**

> `#27` 본문: *"**`UNIQUE(log_id, event_id)`** 로 dedup을 스토어가 강제한다. 충돌은 `errcode: 2067`
> (`SQLITE_CONSTRAINT_UNIQUE`)로 식별해 `duplicate`로 분류한다 (결정 §부수 실측)"*

> `#15` 결정: *"UNIQUE 충돌은 `errcode: 2067`(SQLITE_CONSTRAINT_UNIQUE)로 식별 가능 — dedup의
> `accepted`/`duplicate` 분류 근거로 충분."*

실물 (`src/store.ts:246-256`):

```sql
CREATE TABLE IF NOT EXISTS events (
  seq      INTEGER PRIMARY KEY AUTOINCREMENT,
  log_id   TEXT NOT NULL,
  event_id TEXT NOT NULL,
  payload  BLOB NOT NULL,
  UNIQUE (log_id, event_id)
) STRICT;
```

**컬럼이 넷이다. 출처를 담는 자리가 없다.**

**(b) 서버 발급 read 커서**

> `#27` 본문: *"커서는 **서버 발급 불투명 토큰**이다. 클라이언트는 저장했다 그대로 보낼 뿐이다"* ·
> *"**미지 커서를 판별할 수 있어야 한다**"*

> `#15` 결정: *"커서 인코딩은 `seq` 기반 10진수 또는 base64url … 발급 지점은 이벤트 스토어 조각의
> 계약으로 둔다."*

실물 (`src/store.ts:276-278`, `:288-294`, `:520-534`): 커서는 `seq`의 10진수 문자열이고, 해석은
`SELECT 1 AS ok FROM events WHERE log_id = ? AND seq = ?`(`:418`)의 **존재 확인 한 번**이다.
결과는 `{from, afterSeq}`로 돌아가고 **어디에도 기록되지 않는다** (`readPage`는 `:461-479`에서
읽기만 한다).

**(c) `seq` 전순서**

> `#27` 본문: *"전순서(`§1.4`)의 근거는 단조 증가 정수 하나(`rowid`/`seq`)다. **한 번 확정된 상대
> 순서는 재부팅에도 바뀌지 않는다** (MUST)"*

실물: `seq INTEGER PRIMARY KEY AUTOINCREMENT`. `src/store.ts:270-274`가 그 성질 하나를 더
적는다 — **`seq`는 DB 전체에서 단조 증가한다** (DB는 전체 하나, 로그 구분은 `log_id` 컬럼).

**(d) 단일 프로세스**

> `#15` 결정: *"**서버 프로세스는 하나다.** 단, 이 가정을 코드에 명시적으로 적는다."*

실물: `src/store.ts:39-62`가 전제·깨지는 조건·그때 깨지는 계약을 적었다.

**(e) 실물이 이슈 본문보다 더 말해 주는 것 — append 경로에 출처가 닿지 않는다**

이슈 본문에는 없고 실물에만 있는 사실이고, §Q2.4의 판정이 여기 걸린다.

```
src/store.ts:216    append(logId: string, events: readonly AppendEvent[]): Promise<AppendResult>
src/server.ts:118-124   async function handleAppend(store, broker, logId, rawBody, res)
src/server.ts:554-563   verifyTransportRequest(...) → result.request.logId 만 handleAppend로 간다
```

**스토어의 `append`는 로그 id와 이벤트 배열만 받는다. 누가 밀었는지는 게이트에서 검증되고 그
자리에서 버려진다.**

### Q2.3 P3가 요구하는 것과 실물의 대조

P3의 감지 조건은 *"같은 source id가 **어긋난 커서 위치에서 push**하면"* 이다. 이 문장이 요구하는
것은 셋이고, **셋 다 없다.**

| P3가 요구하는 것 | 오늘 | 근거 |
|---|---|---|
| ① push 요청에 **source id**가 실린다 | **없다** | `0002:177-181`: `type AppendRequest = { events: Event[] }`. 봉투는 `{id, payload}`뿐(`0002:84-89`)이고 `event.ts` 게이트가 미정의 필드를 `400 invalid_event`로 거부한다 |
| ② push 요청에 **커서 위치**가 실린다 | **없다 — 그리고 금지에 가깝다** | `0002:504`(§7.2): *"append는 조건부가 아니다. `If-Match`류 헤더도, **"커서가 X일 때만 써라"도 없다**"* |
| ③ 서버가 **source별 push 진행 위치**를 들고 있다 | **없다** | `src/store.ts:246-256` 스키마에 그런 컬럼·테이블이 없고, `append`(`:427-459`)가 쓰는 것은 `events` 한 테이블뿐이다 |

②가 특히 중요하다. **커서를 push에 싣는 것은 스펙이 우연히 빠뜨린 것이 아니라 §7.2가 의도적으로
배제한 것이다.** 그 절의 제목이 *"조정(mutual exclusion)은 여기 없다"* 이고, `0002:507-509`가 이유를
적었다 — *"기억 로그(append-only·결과적 일관성)와 상호배제(강한 일관성)는 요구가 반대이므로 같은
자리에 두지 않는다."* P3를 커서 비교로 세우려면 그 결정을 뒤집어야 한다.

`#27`의 커서가 **read 커서**라는 #31의 관측도 실물에서 확인된다: 커서가 나타나는 자리는
`GET …/events?after=`(`0002:280`), `GET …/subscribe?after=`(`0002:365`), 그리고 응답의
`cursor` 필드뿐이다. **append 방향에는 커서가 없다.**

### Q2.4 두 replica의 구체적 인터리브

사람이 `mori` 프로젝트 폴더를 `cp -r`로 복사했다. 원본 R1과 사본 R2가 **둘 다 `.mori/`의 replica id
`rep_A`를 자칭한다.** 둘 다 같은 로그 `L`에 push한다. 로그 `L`에는 이미 40건이 있다 (`seq` 1..40 중
`L`의 것). 서버가 각 단계에서 **무엇을 보는지**를 함께 적는다.

**1. R1이 자기 첫 이벤트를 민다.**

```
POST /v1/logs/L/events      Authorization: Bearer <워크스페이스 토큰 W1>
{ "events": [ { "id": "ev-101", "payload": {...} } ] }
```

서버: `verifyTransportRequest`가 토큰을 검증하고 `logId=L`을 뽑는다. `handleAppend`는 토큰을 받지
않는다(`server.ts:118-124`). `store.append('L', [ev-101])` → `BEGIN IMMEDIATE` → `INSERT` → `seq=41`
→ `COMMIT` → `{accepted:[{id:"ev-101",cursor:"41"}], duplicate:[]}`.

> **서버가 본 것:** `log_id='L'`, `event_id='ev-101'`, payload 바이트. **끝이다.**
> 이 요청이 R1에서 왔다는 사실을 가리키는 바이트가 저장된 행에 하나도 없다.

**2. R2가 (R1의 존재를 모른 채) 자기 첫 이벤트를 민다.**

```
POST /v1/logs/L/events      Authorization: Bearer <워크스페이스 토큰 W2>
{ "events": [ { "id": "ev-102", "payload": {...} } ] }
```

서버: `seq=42`, `accepted`.

> **서버가 본 것:** 새 `event_id` 하나. 1번과 2번이 **서로 다른 사본**에서 왔다는 것을 가리키는
> 바이트는 요청 어디에도 없다. 토큰이 다르다(W1≠W2)는 사실은 게이트가 알지만 **스토어에 닿지 않고,**
> 그리고 애초에 **두 워크스페이스가 같은 로그를 동시에 여는 것은 정상이다** —
> `0003:1045`: *"**여러 작업공간이 같은 로그를 동시에 열 수 있다** (MUST 허용). 서버는 그것을
> 거부하지 않고, 경고하지도, 순서를 정하지도 않는다."*

**3. R2가 자기 로컬 오프셋으로 따라잡는다 — "어긋난 커서 위치"가 실제로 나타나는 자리.**

```
GET /v1/logs/L/events?after=39
```

R2는 복사되기 전 시점의 커서 `39`를 들고 있고, R1은 이미 `41`을 봤다. **이것이 P3가 말하는
"어긋난 커서 위치"다.** 서버: `#resolveStart`(`store.ts:520-534`)가 `SELECT 1 … seq=39` →
있으므로 `{from:'known', afterSeq:39}` → `seq > 39`인 행을 앞에서부터 읽어 돌려준다.

> **서버가 본 것:** *"어떤 요청자가 39 다음을 원한다."* **누가 원하는지 모르고, 이 조회를
> 기록하지 않는다.** `readPage`는 `SELECT` 둘뿐이다(`store.ts:461-479`). 그러므로 4번 시점에
> 서버에게 *"`rep_A`가 39에 있었다"* 는 사실이 **존재하지 않는다.**

**4. R1이 타임아웃 뒤 재시도한다.**

```
POST /v1/logs/L/events   { "events": [ { "id": "ev-101", … } ] }
```

서버: `INSERT` → `SQLITE_CONSTRAINT_UNIQUE`(2067) → `#insertOne`의 `catch`가
`SELECT seq … event_id='ev-101'` → `duplicate:[{id:"ev-101",cursor:"41"}]`.

> **서버가 본 것:** *"이미 있는 id."* **이것이 포크 신호로 보이는 유일한 자리인데,
> `0002:265-267`이 이것을 정상 재시도로 규정했다** — *"같은 `id`를 다시 밀면 `duplicate`로
> 분류되므로 재시도는 언제나 안전하다."* 서버는 *"같은 replica의 재시도"* 와 *"복제된 replica의
> 겹친 id"* 를 구분할 근거를 하나도 갖고 있지 않다.

**5. 그리고 진짜 피해가 여기서 난다 — id가 replica-로컬이면 R2의 이벤트가 조용히 사라진다.**

01:52 결정은 replica id를 로컬 state로 두었으므로, 클라이언트가 이벤트 id를 `rep_A-7`처럼 자기
replica id + 로컬 카운터로 만드는 것은 자연스러운 구현이다. R1과 R2가 **둘 다 `rep_A`를 자칭하므로**
둘 다 `rep_A-7`을 만든다.

```
R1: { "events": [ { "id": "rep_A-7", "payload": <R1의 기억> } ] }   → accepted, seq=43
R2: { "events": [ { "id": "rep_A-7", "payload": <R2의 기억, 다른 내용> } ] }  → duplicate, cursor "43"
```

> **R2의 그 기억은 로그에 들어가지 않았고, R2는 `200`을 받았다.** `0002:196-198`:
> *"**first-write-wins**이며, 이건 에러가 아니다 … 서버는 payload 바이트를 **비교하지 않아도 된다**
> — 같은 id로 다른 바이트를 밀면 먼저 것이 남고 나중 것은 조용히 버려진다."*
> `src/store.ts:504-513`이 그대로 구현한다 — `duplicate`로 밀어 넣을 뿐 바이트를 보지 않는다.

**5번이 판정의 핵심이다.** UNIQUE는 이 시나리오에서 감지를 **제공하지 않는다.** 그것이 하는 일은
두 사본의 충돌을 정상적인 `duplicate`로 접어 **조용한 유실을 만드는 것**이다. 결정문이 *"중복 노드
id 문제의 정석 해법"* 이라고 부른 것은 UNIQUE 제약이 **출처를 키에 포함할 때** 성립하는 이야기인데,
이 스키마의 키는 `(log_id, event_id)`이고 **출처가 없다**.

### Q2.5 그렇다면 오늘 존재하는 "부품"은 무엇인가

전혀 없지는 않다. **정확히 하나 있고, 그것은 UNIQUE도 커서도 아니다.**

`0002:522-526` (§8 미결 3):

> **같은 id·다른 바이트.** §2.1은 first-write-wins에서 멈춘다. payload는 불투명하지만 **바이트
> 비교는 해석 없이도 가능하므로**, 서버가 불일치를 감지해 응답에 표시하는 선택지가 있다. 지금
> 정하지 않는 이유: 그러려면 서버가 기존 바이트를 읽어와야 해서 append 경로가 비싸지는데, 그 비용을
> 감수할 만한 실제 오용 사례를 **아직 못 봤다.** 정한다면 `duplicate` 항목에 플래그를 더하는 형태가
> 될 것이다.

**P3가 바로 그 "실제 오용 사례"다.** §Q2.4-5의 인터리브에서 `duplicate`의 바이트 불일치는
*"두 사본이 같은 id 공간을 쓰고 있다"* 의 강한 신호다 — 정상 재시도는 **정의상 같은 바이트를**
다시 보내기 때문이다(`0002:265`: *"같은 요청을 그대로 다시 보낸다"*).

한계도 정직하게 적는다: 이것은 **확률적·사후적** 신호다. 두 사본의 id가 겹칠 때만, 그리고 겹친
뒤에만 울린다. **재발급을 지시할 근거로는 쓸 수 있어도, 조용한 유실을 막지는 못한다** — 신호가
울리는 시점에 R2의 기억은 이미 버려진 뒤다. 그러므로 이것은 감지의 **보조**이지 정본이 될 수 없다.

### Q2.6 감지를 가능하게 하는 최소 추가 상태

**커서를 전혀 쓰지 않는 경로가 있다.** P3의 문면("어긋난 커서 위치")은 그 문면대로 세우면 §7.2를
뒤집어야 하지만(§Q2.3-②), 그것이 잡으려는 사실 — *"같은 source id가 두 자리에서 살아 있다"* — 은
커서 없이 판정할 수 있다.

**필요한 최소 상태는 둘이다.**

1. **이벤트에 남는 출처 축** — §Q1.5의 (라). `events`에 `workspace_id` 컬럼 하나. 없으면 어떤 감지도
   불가능하다. 이것이 P2(a)와 **공유되는 부품**이고, 두 문제를 한 조각이 받는다는 뜻이다.
2. **replica → workspace 매핑** — §Q1.6. 제어 평면이 `POST /v1/workspaces`(`0003:683-686`)에서
   replica를 받아 `WorkspaceRecord`(`0003:880-889`)에 적는다.

**그 위에서 감지 규칙은 시간 겹침이다:** 같은 `replicaId`로 열린 두 작업공간의 활성 구간이 겹치면
포크다. 활성 구간의 정본을 제어 평면이 이미 들고 있다 — `openedAt` · `lastHeartbeatAt` · `endedAt`,
그리고 `0003:662-663`의 *"`abandoned` 판정은 조회 시점에 `lastHeartbeatAt + gracePeriod`로
계산한다"*.

이 경로의 값:

- **커서를 push에 싣지 않는다** → `0002:504`(§7.2)를 건드리지 않는다.
- **전송 평면에 새 판정이 없다** → 감지는 제어 평면 안에서 끝난다. `0003:35-37`이 금지한 방향
  (제어 평면이 이벤트를 읽는 것)도 피한다 — 겹침 판정은 `WorkspaceRecord`만 보고 이벤트를 보지 않는다.
- **`source별 위치 테이블`이 필요 없다** → §Q2.3-③의 상태를 세우지 않아도 된다.

**한계도 적는다.** 시간 겹침은 *"두 사본이 동시에 살아 있다"* 를 잡지, *"한 사본이 죽은 뒤 다른
사본이 이어서 쓴다"* 를 잡지 못한다. 후자는 `cp -r` 후 한쪽만 쓰는 경우이고, 그때는 두 사본이 같은
id를 만들 때만(§Q2.5의 바이트 불일치) 드러난다. **둘을 겹쳐야 커버가 넓어진다.**

**그리고 감지해도 지시할 자리가 없다.** 결정문의 *"hub가 포크를 감지해 **재발급을 지시한다**"* 의
뒷부분이 오늘 와이어에 자리가 없다:

- 전송 평면: `0002:148-163`의 에러 표에 그런 `code`가 없고, `0002:25` — *"이 셋 말고 전송 평면에
  라우트를 추가하지 않는다."*
- subscribe의 `reset` 프레임은 후보처럼 보이지만 아니다. `0002:443-444`가 못박았다 —
  *"`reset`의 `reason`은 사람이 읽는 설명이다. 클라이언트의 대응은 이유와 무관하게 하나다: pull로
  따라잡고 다시 연다."* 지시를 실으면 그 조항이 깨진다.
- 제어 평면: `0003:23-33`의 라우트 여섯 중 지시를 실을 응답은 하트비트(`§4.3`)가 가장 가깝다.
  **재발급 지시는 제어 평면 응답에 서는 것이 자연스럽고, 그것이 §Q5 S2의 실질이다.**

### Q2.7 "지금 넣어야 하는 것"과 "나중에 더해도 되는 것"

#31은 `#27`이 진행 중임을 전제로 이 갈라 적기를 요구했다. §0.3대로 `#27`은 머지됐으므로 시제를
**"머지된 것을 되돌려야 하는가 / 나중에 더해도 되는가"** 로 읽는다.

**나중에 더해도 되는 것 — 사실상 전부.** 근거 셋:

1. **스키마 마이그레이션 자리가 이미 열려 있다.** `src/store.ts:101`의 `SCHEMA_VERSION = 1`과
   `applySchema`(`:374-385`)가 *"이보다 **높은** 버전이 적혀 있으면 열지 않는다"* 로 위쪽만 막고,
   같거나 낮은 쪽은 열어 뒀다. 컬럼 추가는 `SCHEMA_VERSION`을 2로 올리며 `ALTER TABLE`을 얹는
   평범한 마이그레이션이다.
2. **커서 표현이 바뀌어도 계약이 흡수한다.** `src/store.ts:271-274`가 그 경로를 이미 적었다 —
   *"로그 사이를 완전히 가리려면 커서를 로그별 시퀀스로 바꿔야 한다 — 그 변경은 `§3.2`의 미지 커서
   경로가 이미 흡수한다(재구축된 커서 표현은 미지 커서다)."* `0002:317-321`이 그 조항이다.
3. **감지 규칙 자체가 전송 평면 밖에 선다**(§Q2.6). 전송 평면에 넣을 것이 애초에 컬럼 하나뿐이다.

**되돌릴 수 없는 것 — 하나뿐이고, 그것이 이 산정의 시한을 정한다.**

로그는 append-only이므로 **컬럼을 나중에 추가해도 그 이전에 쌓인 이벤트의 출처는 영원히 비어 있다.**
`0002:110`이 수정을 금지했으므로 소급해 채울 수도 없다. 즉 **출처 축이 서기 전에 흐른 트래픽만큼
"출처를 모르는 구간"이 로그에 영구히 남는다.**

**그 구간의 오늘 크기는 0이다.** 이 리포에 배포 설정이 없다 — `.github/workflows/`에 `ci.yml`
하나뿐이고, 컨테이너·플랫폼 설정 파일이 리포 루트에 없다. 서버를 띄우는 것은 테스트뿐이다.
**따라서 시한은 `#27`의 머지가 아니라 첫 실 트래픽이고, 지금 아무것도 되돌리지 않아도 잃는 것이
없다.** 이것이 §Q3 판정의 근거다.

## Q4 — join 진입점이 hub에 요구하는 것

01:59 보강이 남긴 설계 제약:

> **join은 스크립트화 가능한 단일 진입점(CLI 한 명령, 비대화형 옵션 포함)이어야 한다.**
> GUI는 그것을 감싸는 껍질이다.

CLI 자체는 mori 쪽 일이므로 설계하지 않는다. **hub가 받아야 할 것만 적는다.**

### Q4.1 join이 부르는 hub 표면 — 셋은 있고 둘은 없다

`mori join <폴더>`를 hub 호출로 번역하면 네 단계이고, 전부 **제어 평면**이다 (전송 평면에는 로그를
만드는 경로도 토큰을 만드는 경로도 없다 — `0003:38-39`).

| 단계 | 필요한 hub 표면 | 오늘 있는가 |
|---|---|---|
| ① 새 프로젝트를 만들며 join | `POST /v1/logs` (`0003:184-219`, §2.1) | **있다** |
| ② 기존 프로젝트에 join — 그 `logId`를 얻는다 | 로그 조회·해석 표면 | **없다 (공백 1)** |
| ③ 작업 시작 — 토큰을 받는다 | `POST /v1/workspaces` (`0003:673-698`, §4.2) | **있다.** 단 join과 같은 사건이 아니다 (§Q4.3) |
| ④ replica를 hub에 알린다 | replica 축을 받는 자리 | **없다 (공백 2)** |

**공백 1 — 로그 조회 표면이 없다.** `0003:23-33`의 라우트 표 여섯 중 조회는
`GET /v1/workspaces`·`GET /v1/workspaces/{id}` 둘뿐이다. **`GET /v1/logs`가 없다.** 그런데 ②는
join의 기본 경로다 — 01:59 보강의 북극성 UX(*"프로젝트 폴더를 워크스페이스에 끌어다 놓으면"*)에서
워크스페이스는 이미 존재하고, 드래그는 대개 **기존 프로젝트에 붙이는 행위**다.

**공백 2 — `0003`에 `replica`라는 낱말이 없다**(§0.5 실측). 제어 평면이 아는 주체는 subject와
workspace뿐이다. P3의 *"hub가 포크를 감지해 재발급을 지시한다"* 가 성립하려면 hub가 replica를
알아야 하므로, **이 공백은 Q2의 결론과 같은 자리를 가리킨다** — §Q5 S2가 둘을 함께 받는다.

### Q4.2 비대화형이 되려면 무엇이 인자로 와야 하는가

`0003`의 계약에서 곧장 따라 나오는 것 셋:

1. **런처 자격증명.** `0003:75` — *"제어 평면의 모든 라우트는 런처 자격증명을 요구한다 (MUST)."*
   그러므로 join은 자격증명을 인자·환경변수로 받아야 하고 대화형 프롬프트로 물을 수 없다.
   **그런데 그 자격의 형태가 아직 미정이다** — `0003:1086-1091` (§8 미결 2). **join의 비대화형
   성질이 이 미결에 직접 걸린다.**
2. **`Idempotency-Key`.** `0003:147-148` — *"`POST /v1/logs`와 `POST /v1/workspaces`는
   `Idempotency-Key`를 요구한다 (MUST). 없으면 `400 missing_idempotency_key`."* 스크립트가 자동
   재시도하는 것이 비대화형의 전제이므로, **join은 키를 스스로 생성하고 재시도에 걸쳐 유지해야
   한다.** 매 시도마다 새 키를 만들면 멱등성이 무의미해지고 프로젝트가 둘 생긴다.
3. **주체는 인자가 될 수 없다.** `0003:84-85` — *"**주체를 요청 본문·쿼리로 지정할 수 없다**
   (MUST NOT). 주체는 자격증명에서만 해석된다."* 즉 `mori join --as <사람>` 같은 옵션은 hub가 받지
   않는다. 계정을 바꾸는 것은 자격증명을 바꾸는 것이다.

### Q4.3 겹침 — `0003`의 어느 절과 겹치는가

| join이 하는 일 | 겹치는 절 | 겹침의 성격 |
|---|---|---|
| 프로젝트를 만든다 | **`0003 §2.1`** `POST /v1/logs` (`:184-219`) | **완전히 겹친다.** join의 ①은 이 라우트 그대로다. 새 라우트가 필요 없다 |
| 자격을 확인한다 | **`0003 §3.6`** grant 판정 (`:530-548`) | **이음매로 겹친다.** *"이 사람이 이 프로젝트에 join할 수 있는가"* 가 정확히 grant 판정이고, `0003:543-545`가 *"판정 자체는 반드시 일어난다 (MUST). 그 판정의 **규칙**은 … 이 문서의 범위가 아니다"* 로 규칙을 §7.3(`:1053-1061`)로 넘겼다. **join은 그 규칙 없이 완성되지 않는다** |
| 작업을 시작한다 | **`0003 §4.2`** `POST /v1/workspaces` (`:673-746`) | **겹치지만 같은 사건이 아니다** — 아래 |

**join을 `§4.2`에 얹으면 안 된다.** 수명이 다르기 때문이다(§Q1.6): 작업공간은 수 분~수십 분
(`0003:523-524`), join은 클론이 사는 동안 한 번이다. 얹으면 *"join이 작업공간과 같은 사건으로
태어난다"* 가 되어 **작업공간을 열 때마다 join이 다시 일어나고**, 그 순간 01:52 결정의 요지인
*"join은 언제나 명시적 의사표시"* 가 무의미해진다 (스크립트가 세션마다 자동으로 하는 것은 의사표시가
아니다). `0003 §3.1`(`:258-273`)이 토큰을 작업공간과 **같은 사건**으로 묶은 논리는 토큰에 대해서는
옳지만 join에는 적용되지 않는다.

### Q4.4 이 산정이 발견한 걸림돌 — 사람이 프로젝트를 가리킬 방법이 없다

**공백 1(§Q4.1)을 메우려 할 때 곧바로 부딪히는 것이 있고, 이것이 join 설계의 실질적 난점이다.**

`0003:221-235` (§2.2)가 클라이언트의 식별자 제안을 금지하고(`400 client_minted_id`), `0003:234-235`가
이름을 이렇게 처리했다:

> 클라이언트가 원하는 것이 "사람이 읽는 이름"이라면 그건 식별자가 아니라 **메타데이터**다.
> 메타데이터를 어디에 둘지는 제어 평면 데이터 모델의 몫이고 이 문서는 정하지 않는다(§8-3).

그리고 `0003:209-212`가 mint된 `logId`에 **최소 128비트의 예측 불가능한 성분**을 요구했다.

**따라서 오늘 hub에서 프로젝트를 가리키는 유일한 방법은 128비트 난수 문자열을 그대로 들고 있는
것이다.** 북극성 UX에서 사람이 폴더를 끌어다 놓았을 때 *"어느 프로젝트에 붙일까"* 를 고르려면
목록과 이름이 필요한데, **hub 계약에 이름의 자리가 없다.** 로컬 `.mori/`에 캐시하는 것으로는 안
된다 — 2안 결정이 `.mori/`를 통째 gitignore로 두었으므로 새 클론에는 그 캐시가 없고, 애초에 그
상황이 join이 필요한 상황이다.

**그리고 이 질문은 미결 목록에 실려 있지도 않다.** `0003:235`가 메타데이터의 자리를 *"(§8-3)"* 으로
넘겼는데, `0003 §8`의 3번은 **grant 판정의 규칙**이다(`:1092-1093`). §8 아홉 항목 어디에도 로그
메타데이터가 없다 — 즉 **넘겨진 곳이 존재하지 않는 참조다.** (`0003:206`은 같은 질문을 §7.3으로
넘기는데, §7.3(`:1053-1061`)이 받는다고 적은 것은 계정·멤버십·초대이지 로그 메타데이터가 아니다.)
join이 이 질문을 실제로 필요로 하는 첫 소비자이므로, **§Q5 S3이 이 자리를 함께 연다.**

## Q5 — 후속 조각

`#27`–`#30`이 **전부 머지됐으므로**(§0.3) 모든 조각은 그 넷의 **뒤**에 선다. 그래서 순서 줄에는
넷과의 관계에 더해 **조각들 사이의 순서와 실질적 시한**을 함께 적는다.

### S1 — 출처 축의 자리를 스펙에 정한다 (`0002`/`0003` 개정)

§Q1.7의 결론((다)+(라))을 스펙 문면으로 옮긴다: 전송 평면이 **서버 파생 출처 값을 봉투 밖에**
기록한다는 조항, 그것이 `0002:454` 불변식 1을 깨지 않는 이유, `0003`이 replica 축을 갖고
`WorkspaceRecord`가 그것을 싣는다는 조항. 노출은 (라1)로 시작한다.

> **순서:** `#27`–`#30` **전부 뒤**(넷 다 머지됨). **다른 모든 조각의 선행.**
> **실질적 시한: 첫 실 배포보다 앞** — §Q2.7의 "되돌릴 수 없는 것".

### S2 — 포크 감지와 재발급 지시를 제어 평면에 세운다 (`0003` 개정)

§Q2.6대로 **커서가 아니라 활성 구간 겹침**으로 판정 규칙을 세우고, `0002 §7.2`·`0003 §7.2`를
건드리지 않는다는 것을 문면에 남긴다. 재발급 **지시**가 실릴 자리(하트비트 응답이 가장 가깝다)를
정하고, `0002`의 에러 표·라우트 셋을 늘리지 않는다는 것을 확인한다. `#15` 결정의 전제
*"UNIQUE + 커서가 부품을 이미 제공한다"* 가 거짓이라는 것(§Q2.1)을 근거로 함께 적는다.

**여기서 반드시 갈라야 할 것:** 감지가 **advisory**인가 **강제**인가. 강제(재발급 전까지 push
거부)로 가면 그것은 사실상 배타 제어이고, `0002:500-509`·`0003:1036-1051`이 두 평면 **모두에서**
조정을 배제한 것과 부딪힌다. 01:59 보강이 P4를 *"차츰 해결"* 로 내린 것과도 어긋난다.
**advisory로 시작하는 것이 두 문서의 기존 방향과 정합한다.**

> **순서:** **S1 뒤** — 출처 축이 없으면 감지의 재료가 없다(§Q2.6-1).
> `#27`–`#30` 전부 뒤. S3와는 독립이나 §Q4.1 공백 2를 공유하므로 함께 보는 편이 낫다.

### S3 — join이 부를 hub 표면을 정한다 (`0003` 개정)

§Q4.1의 공백 1(로그 조회·해석 표면)과 §Q4.4(이름 메타데이터의 자리 — 오늘 `0003 §8` 어디에도 실려
있지 않은 질문)를 함께 받는다. `0003 §2.1`·`§3.6`·`§4.2`와의 겹침을 §Q4.3대로 명시하고,
**join을 `§4.2`에 얹지 않는다**는 것을 근거와 함께 적는다. `0003:206`·`:235`의 잘못된 전달 참조
(§Q4.4)도 이 조각이 정리한다.

> **순서:** `#27`–`#30` 전부 뒤. **S1과 독립**(파일 교집합은 `0003`뿐이고 절이 다르다).
> **선행 미결 둘에 걸린다** — `0003 §8-2`(런처 자격증명의 형태, `:1086-1091`)와
> `§8-3`(grant 판정 규칙, `:1092-1093` — 규칙 자체는 §7.3 문서의 몫). 그 둘이 열려 있는 동안
> S3는 **표면의 모양까지만** 정할 수 있고 자격·권한 규칙은 정할 수 없다.

### S4 — S1을 코드로 내린다 (`src/store.ts` 스키마 v2 + append 배선)

`events`에 출처 컬럼, `SCHEMA_VERSION` 1 → 2, `src/server.ts:562`가 검증된 토큰을 `handleAppend`에
넘기고 `store.append`가 그것을 기록한다. 와이어 계약은 바뀌지 않는다(§Q3의 `#28` 행).

> **순서:** **S1 뒤**(스펙 없이 구현 코드를 쓰지 않는다 — `CLAUDE.md` 하드 룰 1).
> `#27`–`#30` 전부 뒤. **S2·S3와 병렬 가능.** **첫 실 배포보다 앞**(§Q2.7).

### S5 — "선별 제거"가 무엇을 뜻하는지 정한다 (`0002 §1.4`·`§8-6`·`0003 §8-4` 합동)

§Q1.0의 벽을 정면으로 받는 조각이다. `0002:110`이 삭제를 금지했으므로 되돌림의 실행 형태는
(ⓐ 읽기 경로 필터 — `0002:317-321`의 조용한 누락 금지와 부딪힌다, ⓑ 클라이언트가 읽는 무효 선언 —
`0002:111`의 *"retract는 payload 안의 클라이언트 개념"* 과 정합, ⓒ 보존과 함께 실제 삭제 —
`0002:535-538`·`0003:1094-1096`) 중 하나를 골라야 한다.

> **순서:** **S1 뒤**(출처 축이 없으면 "무엇을 제거할지" 자체를 특정할 수 없다). **가장 뒤.**
> `0002 §8-6`(보존)이 함께 열려야 하므로 이 조각만 앞당길 수 없다.

### S6 — 낡은 코멘트 앵커 정정 (잡무)

§0.4의 넷. `src/store.ts:8`·`:263`의 링크와, `#27`·`#31` 이슈 본문의 링크.

> **순서:** 아무 데나. `#27`–`#30`과 무관하고 다른 조각의 선행도 아니다. 코드 주석 한 줄이므로
> 다른 조각에 얹어 처리해도 된다.

### Q5.0 P1·P4는 조각으로 자르지 않는다 — 대신 "막히지 않는다"를 확인한다

01:59 보강이 P1을 *"베스트 에포트로 단순하게 유지"*, P4를 *"차츰 해결"* 로 내렸다. 이 산정이 할 일은
**지금 결정하지 않아도 나중에 막히지 않는지 확인하는 것**이다.

**P1 (부트스트랩 공백) — 막히지 않는다. 단 전제가 하나 붙는다.**

늦은 결속(미귀속으로 쌓다가 join 시 병합)을 서버 계약이 막지 않는다. 근거 셋: 이벤트 `id`를
클라이언트가 만들고(`0002:84-89`), dedup이 멱등이라 나중에 밀어도 안전하며(`0002:265-271`), 미지
커서가 전량 반환이라 새 replica의 부트스트랩이 정상 경로다(`0002:317-321`). **join 뒤에 한꺼번에
밀어도 서버 쪽에서 잃는 것이 없다.**

**전제:** 그 기억들의 이벤트 `id`가 **전역적으로 유일해야** 한다. replica-로컬 카운터로 만들면
§Q2.4-5의 조용한 유실이 P1 경로에서도 그대로 일어난다 — 미귀속으로 쌓은 기억이 join 시점에
`duplicate`로 접혀 사라진다. **이것은 클라이언트(mori) 쪽 규약이지만, 서버 계약이 그것을 강제할 수
없다는 사실**(`0002:196-198`의 first-write-wins, 바이트 비교 없음)**을 여기 적어 둔다.**

**P4 (멀티 replica 락 조정) — 막히지 않는다. 다만 S2와 선이 가깝다.**

두 스펙이 조정을 **양쪽 평면 모두에서** 배제했고(`0002:500-509`, `0003:1036-1051`), 필요해지면
*"이 로그 위도, 이 제어 평면 위도 아닌 다른 자리에 선다"*(`0003:1050-1051`)까지 정해 두었다.
지금 결정하지 않아도 그 자리가 막히지 않는다.

**단, S2가 그 선을 넘기 쉽다.** 포크 감지는 *"같은 source가 두 자리에서 살아 있다"* 를 판정하는
것인데, 그 판정을 **강제**(재발급 전까지 push 거부)로 만들면 배타 제어와 구별되지 않는다.
감지는 사후 관찰이고 조정은 사전 배타라는 차이가 있지만, 강제가 붙는 순간 그 차이가 사라진다.
**S2의 완료 조건에 "advisory인가 강제인가"를 명시적으로 넣어야 하는 이유가 이것이다** (S2 참조).
