# 0001 — 새 프로토콜이 만족해야 하는 것

상태: **초안.** 2026-08-02 설계 논의 갈무리.
근거: mori [#115](https://github.com/shakystar/mori/issues/115), 구 relay 코드 실측.

이 문서는 요구사항만 적는다. 스펙(엔드포인트·스키마)은 다음 문서에서 정한다.
**코드는 스펙이 서기 전에 쓰지 않는다.**

## 0. 전제 — 무엇을 위한 서버인가

mori는 개발자를 좁게 겨냥하지 않는다. **사람들이 협업에 쓰는 하네스**다. 이 한 줄이
서버 요구사항을 바꾼다:

- 혼자 쓰면 hub는 백업에 가깝다. 여럿이 쓰면 hub가 **유일한 공유 지점**이다.
- 따라서 "동료가 내 결정을 언제 보는가"가 곧 협업의 품질이다. 세션 경계 배치 push는
  이 조건을 만족하지 못한다.
- git이 있는 환경을 가정할 수 없다. 정체성·동기화 어느 것도 git 산출물에 의존하면 안
  된다. git은 정체성 파일을 옮기는 여러 운반 수단 중 하나일 뿐이다.

## 1. 계승하는 불변식

구 relay(`memorize_hub/packages/relay`, 434줄)의 **계약**은 옳다. 구현은 버리되 아래
넷은 재발명하지 않는다 — 재발명하면 같은 자리로 돌아온다.

1. **불투명 페이로드.** 서버는 이벤트 내용을 해석하지 않는다. `id` 외에는 아무것도
   요구하지 않는다. E2E 암호화와 두 평면 분리가 여기 걸려 있다.
2. **id 기준 멱등 dedup.** 같은 id를 다시 밀면 무시된다. write-through 재시도를
   공짜로 만드는 근거이며, 이것이 없으면 실시간 push가 성립하지 않는다.
3. **append-only + 순서 보존.** 그리고 미지 커서에는 **전량 반환** — 덜 주는 것보다
   더 주는 것이 안전하다 (클라이언트가 dedup한다).
4. **두 평면 경계.** 전송(dumb)과 제어(smart)를 분리한다. 식별자는 서버가 발급한다
   (server-minted).

## 2. 새로 요구되는 것

### 2.1 서버 → 클라이언트 실시간 경로

구 계약은 **폴링 pull 전용**이다. 협업이 전제면 이건 계약 층의 공백이고, 구현으로
덮을 수 없다. 폴링 주기를 줄여 흉내내면 §3.3의 비용이 그대로 곱해진다.

- 요구: 새 이벤트가 도착하면 구독 중인 replica에 **밀어준다** (SSE/WebSocket 등).
- 폴링은 폴백으로 남긴다 (구독이 끊긴 구간의 복구 경로).

### 2.2 `accepted`의 의미를 내구성으로 못박기

구 계약의 `accepted`는 "받았다"인지 "디스크에 안전하다"인지 말하지 않는다.

이게 왜 중대한가: mori는 샌드박스 격리를 위해 db를 **임시 작업공간 안**에 둔다. 그
작업공간은 작업이 끝나면 지워진다. **push 성공이 "이 작업공간을 죽여도 된다"의 유일한
근거**다. 그 근거가 모호하면 설계 전체가 흔들린다.

- 요구: 성공 응답은 **내구화 완료**를 의미한다. 그렇지 않으면 별도 필드로 구분한다.
- 검증: accept 직후 서버를 `kill -9` 하고, accepted된 이벤트가 남아 있어야 한다.
  (구 구현은 이 시험을 통과하지 못한다 — §3.1)

### 2.3 단건 write-through

기억이 생길 때마다 민다. 배치는 효율 최적화지 기본값이 아니다.

- 구 계약은 이미 이걸 지원한다 (`events` 길이 1). 계약 변경 없음.
- 다만 요청 수가 급증하므로 §3.2·§3.3의 구현 갭이 치명적으로 바뀐다.
- 쓰기 증폭이 문제가 되면 **짧은 debounce(1초 수준)**로 묶는다. 꼬리를 1초로 묶는
  것과 세션 경계까지 늘리는 것은 다른 이야기다.

### 2.4 작업공간 생애 추적

작업공간(임시·격리된 실행 단위 — worktree일 수도, 컨테이너일 수도, 클라우드
샌드박스일 수도 있다)을 **만들고 지우는 주체는 하네스**다. 그러니 flush 보장도
하네스의 몫이다. 서버는 그것이 지켜졌는지 **보이게** 해야 한다.

- 요구: 작업공간 생성·활성·종료를 서버가 안다.
- 그래야 "flush 없이 죽은 작업공간"이 조용히 사라지지 않고 드러난다.

### 2.5 런처가 주입하는 스코프 토큰

신뢰 결정은 샌드박스 **밖**에 있어야 한다. 안에 있는 에이전트가 자기 권한을 스스로
정할 수 있으면 그건 통제가 아니다.

- 리포에 커밋되는 정체성 파일에는 **프로젝트 ID만** 담는다. **hub 주소·자격증명은
  절대 담지 않는다.** 그래야 악의적 fork가 정체성 파일을 조작해도 기억이 남의 hub로
  나가지 않는다 — 안에 있는 에이전트는 런처가 준 hub 외에는 갈 수 없다.
- 토큰은 작업공간 단위로 발급하고, 접근 범위를 서버가 강제한다.
- 구 relay는 **릴레이 전체에 토큰 하나**이고 프로젝트별 스코프가 없다
  (`packages/relay/src/server.ts:111`). 권한을 gateway가 지는 구조라 그 자체로 틀린
  것은 아니지만, **relay를 클라이언트에 직접 노출하면 즉시 cross-tenant 구멍**이다.
  작고 단순해서 직접 붙이고 싶어지는 물건이므로 여기 못박아 둔다.

## 3. 구 구현에서 반복하지 말 것

구 relay 434줄 실측(2026-08-02). 넷 다 **구현** 결함이며 와이어에는 보이지 않는다 —
그래서 "구현이 나쁘다"가 프로토콜 재정의의 근거는 아니었다. 재정의의 근거는 §2.1이다.
다만 새로 짤 때 같은 함정에 다시 빠지지 않도록 남긴다.

### 3.1 fsync 없음 — 정확성 문제

`store.ts:123`의 `appendFile`은 OS 페이지 캐시까지만 쓴다. 그런데 `server.ts:138-145`는
그 직후 `accepted`를 돌려준다. 호스트가 그 사이에 죽으면 **클라이언트가 안전하다고
믿은 이벤트가 조용히 사라진다.** §2.2가 요구하는 것이 정확히 이 갭이다.

### 3.2 전량 인메모리

`EventStore.open`(`store.ts:46-56`)이 부팅 시 모든 프로젝트의 ndjson 전체를 메모리에
올리고, 이후로도 계속 들고 있다. append-only 기억 서버에서 이건 디스크를 늘려도 못 푸는
천장이다.

### 3.3 pull이 O(n)

`store.ts:171`의 `findIndex`가 요청마다 전체 배열을 훑는다. write-through(이벤트 수
급증) × 협업(pull 빈도 급증)이 겹치면 요청 비용이 이력 길이를 따라 자란다.

### 3.4 부팅 시간이 선형으로 증가

hydrate가 전 이벤트를 `JSON.parse`한다. 스냅샷도 compaction도 없어서 재배포마다
시작이 느려진다. 콜드 스타트 경로(§2.1의 구독 복구, 신규 replica 부트스트랩)도 같은
비용을 문다.

## 4. 미결

1. **로컬 데몬(“로컬 hub”)을 둘 것인가.** 작업공간 밖 프로세스가 내구 저장소를 소유하고
   스코프된 API만 노출하면, 전역 폴더 화이트리스트 없이 격리를 지키면서 임시 작업공간의
   소실·콜드 스타트·hub 장애를 동시에 푼다. 대신 mori가 CLI에서 **상주 서비스**로
   성격이 바뀐다. 머신 자체가 샌드박스인 경우(클라우드 에이전트)엔 데몬을 둘 곳이
   없으므로 직접 hub로 가야 하는데, 양쪽이 같은 프로토콜이면 클라이언트 입장에서 동작은
   동일하다.
2. **조정(mutual exclusion)을 서버가 질 것인가.** 지금 플릿의 이슈 점유는 GitHub 라벨이
   직렬화하므로 서버 CAS가 필요 없다. 협업 하네스 일반으로 넓히면 필요해질 수 있으나,
   기억 로그(append-only·결과적 일관성)와 상호배제(강한 일관성)는 요구가 반대이므로
   **같은 자리에 두지 않는다**는 것까지만 정해져 있다.
3. **구 인스턴스 처리.** `memorize-hub-shakystar.fly.dev`(구)와 `memorizehub.com`이 둘 다
   살아 있다. 통합 시점과 방식 미정.
