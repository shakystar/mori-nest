# 0003 — 제어 평면 스펙 (식별자 발급 / 작업공간 토큰 / 작업공간 생애 추적)

상태: **초안.** 2026-08-04 작성.
근거: [`0001-protocol-requirements.md`](./0001-protocol-requirements.md) §1.4·§2.4·§2.5,
[`0002-transport-spec.md`](./0002-transport-spec.md) §1.1·§1.2·§5·§8-1·§8-2,
mori-nest [#4](https://github.com/shakystar/mori-nest/issues/4),
mori [#115](https://github.com/shakystar/mori/issues/115).

이 문서는 **제어 평면(smart)만** 정한다. 0001 §1.4가 전송/제어 두 평면 경계를 계승할
불변식으로 세웠고, 0002가 그 경계의 전송 쪽을 정하면서 제어 쪽을 향한 부채를 명시적으로
남겼다(0002 §8-1·§8-2). 이 문서가 그 부채를 갚는다.

**0002는 머지된 계약이다. 이 문서는 그 위에 얹는다** — 전송 평면의 라우트·스키마·상태코드를
바꾸지 않고, 0002가 성질로만 요구한 것(토큰이 자체 검증 가능해야 한다)을 발급 쪽에서 만족하는
형태를 정한다.

이 문서 안에서 **MUST / MUST NOT / MAY**는 계약이다. 그 외 서술은 근거다.

## 0. 이 문서가 정하는 것

제어 평면에는 경로가 여섯이다.

| 경로 | 메서드 | 라우트 | 하는 일 |
|---|---|---|---|
| 로그 발급 | `POST` | `/v1/logs` | 서버가 `logId`를 mint한다 (§2) |
| 작업공간 개시 | `POST` | `/v1/workspaces` | 작업공간을 열고 **그 자리에서 토큰을 발급한다** (§3, §4.2) |
| 하트비트 | `POST` | `/v1/workspaces/{workspaceId}/heartbeat` | 살아 있음을 알리고 **토큰을 갱신한다** (§4.3) |
| 종료 선언 | `POST` | `/v1/workspaces/{workspaceId}/close` | 작업공간을 끝냈다고 선언한다 (§4.4) |
| 폐기 | `POST` | `/v1/workspaces/{workspaceId}/revoke` | 갱신을 끊는다 (§3.5, §4.5) |
| 조회 | `GET` | `/v1/workspaces`, `/v1/workspaces/{workspaceId}` | 작업공간 상태를 본다 (§4.6) |

- 위 표에 없는 메서드는 `405`다 (§1.3).
- **제어 평면은 이벤트를 읽지도 쓰지도 않는다** (MUST NOT). 로그의 내용·길이·커서는 이 문서
  어디에도 나오지 않는다. 커서는 전송 평면이 발급한 불투명 토큰이고(0002 §1.4), 제어 평면이
  그것을 해석하기 시작하면 두 평면 경계가 반대 방향으로 무너진다.
- **전송 평면에는 로그를 만드는 경로도, 토큰을 만드는 경로도 없다.** 0002 §0이 라우트를 셋으로
  못박았고 이 문서는 그것을 늘리지 않는다.

## 1. 공통 계약

### 1.1 베이스 URL과 두 개의 자격

제어 평면의 베이스 URL도 **런처가 주입한다.** 클라이언트는 그것을 리포에 커밋되는 정체성 파일
등 다른 곳에서 유도하지 않는다 (MUST NOT) — 0001 §2.5, 0002 §1.1과 같은 규칙이다. 정체성
파일에는 프로젝트 ID만 담기고 hub 주소·자격증명은 담기지 않는다.

이 시스템에는 **서로 다른 두 개의 자격(credential)** 이 있다.

| 자격 | 누가 든다 | 어디서 통한다 | 이 문서가 정하는 것 |
|---|---|---|---|
| **런처 자격증명** | 샌드박스 **밖**의 런처 | 제어 평면 (이 문서의 여섯 라우트) | 형태·발급은 **비범위**. 이 문서는 "이미 자격이 있는 주체"를 전제로 시작한다 |
| **작업공간 토큰** | 샌드박스 **안**의 에이전트 | 전송 평면 (0002의 세 라우트) | 발급·스코프·수명·갱신·폐기 (§3) |

둘 다 `Authorization: Bearer <credential>`로 실린다. 헤더 이름이 같다는 것이 두 자격을 섞어도
된다는 뜻은 아니다:

- **두 자격은 서로의 평면에서 통과할 수 없어야 한다** (MUST). 작업공간 토큰으로 제어 평면
  라우트를 호출하면 `401 unauthenticated`이고, 런처 자격증명으로 전송 평면 라우트를 호출하면
  0002 §1.2의 `401 unauthenticated`다.
- 작업공간 토큰 쪽에서 이것을 보장하는 것이 `audience` 클레임이다 (§3.2, §3.3). 런처
  자격증명의 형태는 이 문서 밖이지만, **작업공간 토큰과 구분 가능해야 한다**는 것은 계약이다
  (MUST).
- 이 분리가 없으면 샌드박스 안의 에이전트가 자기 전송 토큰을 그대로 제어 평면에 들이밀어
  토큰 발급을 시도할 수 있다. §3.7이 막으려는 것이 정확히 그것이고, 여기가 그 첫 번째 자물쇠다.

토큰을 **쿼리스트링·경로에 싣는 것을 금지한다** (MUST NOT) — 0002 §1.2와 같은 이유(액세스
로그·프록시 로그·리퍼러에 남는다).

### 1.2 주체 — 발급을 요청할 수 있는 것은 런처뿐이다

**제어 평면의 모든 라우트는 런처 자격증명을 요구한다** (MUST). 신뢰 결정은 샌드박스 **밖**에
있어야 하고, 안에 있는 에이전트가 자기 권한을 스스로 정할 수 있으면 그건 통제가 아니다
(0001 §2.5).

- 각 요청은 하나의 **주체(subject)** 로 해석된다. 주체가 무엇인지(계정인지, 기계인지, 조직
  구성원인지)와 그 자격이 어디서 오는지는 **이 문서의 범위가 아니다** — 계정·멤버십·초대는
  별도 문서가 받는다.
- 이 문서가 정하는 것은 **주체가 요청에 어떻게 걸리는가**다: 조회는 주체가 연 작업공간만
  돌려주고(§4.6), 발급은 주체가 grant할 수 있는 로그만 스코프에 실을 수 있다(§3.6).
- **주체를 요청 본문·쿼리로 지정할 수 없다** (MUST NOT). 주체는 자격증명에서만 해석된다.
  주체가 파라미터가 되는 순간 그 파라미터가 열거·사칭 경로가 된다.

### 1.3 에러 형태와 상태코드

**에러 본문은 0002 §1.5의 형태를 그대로 쓴다** (MUST).

```ts
type ErrorResponse = {
  error: {
    code: string              // 기계가 분기하는 안정된 문자열
    message: string           // 사람이 읽는 설명
    details?: Record<string, unknown>
  }
}
```

같은 클라이언트가 두 평면을 모두 호출하는데 에러 파싱을 두 벌 갖게 할 이유가 없다. `code`가
안정된 계약이고 `message`는 분기 근거가 아니라는 성질도 같다.

- **`message`·`details`에 토큰 값을 싣지 않는다** (MUST NOT) — 0002 §1.5와 같다. 이 문서에서는
  발급 자체를 다루므로 §3.8에서 한 번 더 못박는다.

| 상태 | `code` | 언제 |
|---|---|---|
| `400` | `malformed_request` | 본문이 JSON이 아니거나, 스키마에 **정의되지 않은 최상위 필드**가 있다 |
| `400` | `client_minted_id` | 요청이 서버가 발급할 식별자를 제안했다 (§2.2) |
| `400` | `empty_scope` | `logs`가 없거나 빈 배열 (§3.6) |
| `400` | `invalid_log_id` | `logs`의 원소가 0002 §1.1 정규식에 맞지 않는다 |
| `400` | `invalid_state_filter` | `state` 쿼리가 §4.1의 상태 이름 중 하나가 아니다 (§4.6) |
| `400` | `invalid_cursor` | 목록 조회의 `after`를 해석할 수 없다 (§4.6) |
| `400` | `missing_idempotency_key` | 멱등성이 요구되는 라우트에 `Idempotency-Key`가 없다 (§1.4) |
| `401` | `unauthenticated` | 자격 부재·형식 오류·검증 실패, 또는 작업공간 토큰으로 호출 (§1.1) |
| `403` | `not_grantable` | 요청한 로그 중 이 주체가 grant할 수 없는 것이 있다 (§3.6) |
| `404` | `workspace_not_found` | 없는 작업공간 **또는 다른 주체의 작업공간** (구분하지 않는다) |
| `405` | `method_not_allowed` | §0 표에 없는 메서드 |
| `409` | `workspace_not_active` | 이미 끝난 작업공간에 대한 하트비트·종료·폐기, 또는 종단 상태에서의 멱등 재시도 (§4.1, §4.2) |
| `409` | `idempotency_key_reused` | 같은 `Idempotency-Key`, 다른 요청 본문 (§1.4) |
| `413` | `request_too_large` | 요청 본문이 한도 초과. `details.maxRequestBytes` 필수 |
| `429` | `rate_limited` | 유량 제한. `Retry-After` 헤더 필수 |
| `500` | `internal` | 그 외 서버 결함 |
| `503` | `not_durable` | 상태 전이를 내구화할 수 없다 (§4.1) |
| `503` | `unavailable` | 셧다운 중·의존 저장소 접근 불가. `Retry-After` 권장 |

- **정의되지 않은 최상위 필드를 조용히 무시하지 않는다** (MUST NOT). 무시하면 클라이언트는 자기가
  보낸 것이 반영됐다고 믿는다. 특히 식별자를 제안한 경우가 그런데, 그건 더 명확한
  `client_minted_id`로 갈린다 (§2.2).
- **`404 workspace_not_found`는 존재 여부와 무관하게 같다** (MUST) — 없는 id와 남의 id에 대한
  응답이 갈리면 그 자체가 열거 오라클이다. 0002 §1.2가 `403 out_of_scope`에 대해 세운 규율과
  같은 것이고, 제어 평면에서는 라우트가 주체 소유이므로 `404`가 그 자리를 맡는다.

### 1.4 재시도와 멱등성

제어 평면의 요청은 **자원을 만든다.** 타임아웃·`5xx`·연결 끊김을 만난 런처가 그냥 재시도하면
로그가 둘 생기거나 작업공간이 둘 열린다. 전송 평면은 이 문제를 이벤트 `id` 기준 dedup으로 풀었지만
(0002 §2.4), 제어 평면에는 클라이언트가 정하는 id가 없다 — 정의상 서버가 mint하기 때문이다(§2.2).

그래서 멱등성 키를 쓴다.

```
Idempotency-Key: <클라이언트가 생성한 문자열, ^[A-Za-z0-9_.:-]{1,128}$>
```

- **`POST /v1/logs`와 `POST /v1/workspaces`는 `Idempotency-Key`를 요구한다** (MUST).
  없으면 `400 missing_idempotency_key`.
- 같은 주체가 같은 키로 같은 본문을 다시 보내면 서버는 **처음의 결과를 그대로 다시 돌려준다**
  (MUST) — 같은 상태코드, 같은 본문. 자원을 새로 만들지 않는다. 예외는 둘이고, **둘 다 §4.2의
  작업공간 개시에만 있다**:
  - **재발급되는 필드는 `token`·`tokenId`·`expiresAt` 셋이다.** 재시도 응답에 같은 토큰을
    실으려면 서버가 토큰 문자열을 보관해야 하는데 그건 §3.8이 금지하므로 재시도는 새 토큰을
    발급하고, 새 토큰은 발급 시점 기준의 새 만료를 갖는다(§3.4). `expiresAt`을 첫 응답 값으로
    고정하면 **이미 지난 시각**이 나가고, 토큰을 파싱할 수 없는 클라이언트(§3.2)에게는 이
    필드가 만료를 아는 유일한 근거이므로 막 받은 유효한 토큰이 만료된 것으로 읽힌다.
  - **작업공간이 이미 종단 상태(§4.1)면 첫 결과를 돌려주지 않고 `409 workspace_not_active`다**
    (§4.2). 발급이 상태 판정을 통과해야 한다는 §4.1의 규율은 멱등 재시도에도 적용된다 —
    그러지 않으면 폐기된 작업공간에 새 토큰이 나가고 §3.5의 폐기 수렴 시간이 깨진다.
- 같은 키로 **다른 본문**을 보내면 `409 idempotency_key_reused`다 (MUST). 조용히 첫 결과를
  돌려주면 클라이언트는 두 번째 요청이 반영됐다고 오인한다.
- **멱등성 키의 네임스페이스는 주체다** (MUST). 키 조회도 충돌 판정도 **요청 주체 안에서만**
  한다. 키는 클라이언트가 고르는 임의 문자열이라(위 정규식) 서로 모르는 주체끼리도 `retry-1`
  같은 값에서 우연히 부딪힌다. 전역 네임스페이스로 두면 그 충돌이 곧 **남의 첫 결과를 받는
  경로**가 되고 — §4.2의 `409`는 `details`에 `workspaceId`·`state`까지 싣는다 — 반대로 자기
  요청이 `idempotency_key_reused`로 막히는 열거 오라클도 함께 생긴다. §1.2의 주체 스코프가
  여기에도 그대로 적용된다는 뜻이다.
- **키 기록과 자원 생성은 원자적이다** (MUST). 같은 키를 담은 요청 두 건이 동시에 도착해도
  자원은 **정확히 하나만** 생긴다. "키가 있는지 보고 없으면 만든다"를 원자적이지 않게 구현하면
  두 요청이 모두 빈 기록을 보고 둘 다 만든다 — 그 순간 이 절 전체가 무의미해진다. 0002 §2.1이
  dedup 판정·기록의 원자성을 요구한 것과 같은 자리다.
- 서버는 멱등성 키를 **최소 24시간** 보관한다 (MUST). 그보다 짧으면 재시도 창이 보관 창을
  넘어서고, 넘어선 재시도는 새 자원을 만든다.
- `close`·`revoke`·`heartbeat`는 키가 필요 없다 — **그 자체로 멱등이다** (§4.3~§4.5). 조회도
  마찬가지다.

## 2. 식별자 발급 — `logId`는 서버가 mint한다

0002 §1.1이 `logId := ^[A-Za-z0-9_-]{1,128}$`로 **모양**만 정하고 발급 절차를 비워 뒀다. 이 절이
그 자리다.

### 2.1 `POST /v1/logs`

```
POST /v1/logs
Authorization: Bearer <런처 자격증명>
Content-Type: application/json
Idempotency-Key: <키>
```

```ts
type CreateLogRequest = Record<string, never>   // {} — 정의된 필드가 없다
```

```ts
type CreateLogResponse = {
  logId: string   // 0002 §1.1의 정규식을 만족한다
}
```

성공 상태코드: **`201 Created`**. 멱등 재시도도 같은 `201`과 같은 본문이다 (§1.4).

- 본문은 빈 객체다. 이름·라벨·소유자 같은 필드를 두지 않은 이유: 그건 제어 평면 **데이터
  모델**의 어휘이고 이 문서의 범위가 아니다(§7.3). 필요해지면 그 문서가 이 스키마를 넓힌다.
- **mint된 `logId`는 0002 §1.1 정규식을 만족한다** (MUST). 전송 평면은 그 정규식만 검증하므로,
  그것을 벗어난 id를 발급하면 발급 즉시 쓸 수 없는 로그가 된다.
- **mint된 `logId`는 최소 128비트의 예측 불가능한 성분을 포함한다** (MUST). 순번·타임스탬프·
  주체 이름에서 유도한 id를 발급하지 않는다 (MUST NOT). 스코프 강제(0002 §1.2)가 있으므로 id를
  맞힌다고 곧바로 접근이 되지는 않지만, 예측 가능한 id는 스코프 부여 실수 한 건의 폭발 반경을
  "그 실수가 닿은 로그"에서 "맞힐 수 있는 모든 로그"로 넓힌다.
- **mint한 `logId`가 이미 존재하면 그 로그를 돌려주지 않는다** (MUST NOT). 다시 mint하거나
  `500 internal`이다. 128비트 난수의 충돌 확률은 무시할 수 있지만, "이미 있으면 그걸 준다"는
  구현은 난수원이 고장 났을 때(엔트로피 고갈, 고정 시드) **서로 다른 주체에게 같은 로그를
  건네준다.** 그 순간 cross-tenant이고, 증상은 발급이 아니라 한참 뒤 전송 평면에서 나타난다.
- 로그 생성은 **작업공간과 독립이다.** 로그는 작업공간보다 오래 산다 — 작업공간은 수 분에서 수십
  분 살고 사라지지만(0001 §2.4), 로그는 그 작업공간들이 남긴 기억을 계속 들고 있다. 그래서 로그
  발급을 작업공간 개시에 묶지 않았다.

### 2.2 클라이언트는 식별자를 제안하거나 고를 수 없다

**요청은 `logId`를 제안할 수 없다** (MUST NOT). 서버는 클라이언트가 제시한 식별자를 받아들이지
않는다 (MUST NOT).

- 요청 본문에 `logId`·`id`·`name` 같은, 서버가 발급할 식별자를 제안하는 것으로 읽히는 필드가
  있으면 **`400 client_minted_id`** 다 (MUST).
- **조용히 무시하고 `201`을 돌려주지 않는다** (MUST NOT). 무시하면 클라이언트는 자기가 고른 id로
  로그가 생겼다고 믿고 그 id로 push하다가 전송 평면에서 `403 out_of_scope`을 받는다 — 원인이
  발급 시점에 있는데 증상은 전송 평면에서 나타난다.
- 이것이 0001 §1.4의 **server-minted** 불변식이 실제로 지켜지는 자리다. 여러 클라이언트가 각자
  만든 id는 충돌하거나 모호해지고(같은 이름의 두 프로젝트, fork, origin 변경), 그 모호함은 공유
  지점에서 곧바로 cross-tenant 문제로 바뀐다.
- 클라이언트가 원하는 것이 "사람이 읽는 이름"이라면 그건 식별자가 아니라 **메타데이터**다.
  메타데이터를 어디에 둘지는 제어 평면 데이터 모델의 몫이고 이 문서는 정하지 않는다(§8-3).

### 2.3 접두사 — 제어 평면은 의미를 두고, 전송 평면은 눈이 없다

0002 §1.1은 전송 평면이 `logId`를 **prefix-blind**하게 다룬다고 못박았다. 그 규율과, 제어 평면이
접두사에 의미를 두는 것은 **양립한다.** 양립하는 이유를 문면에 적는다.

- 두 평면은 같은 문자열을 **다른 깊이로** 본다. 제어 평면에게 `logId`는 자기가 mint한 구조 있는
  문자열이고, 전송 평면에게는 정규식 검증과 스코프 대조만 하는 불투명 키다. 문자열 안에 구조가
  있다는 사실 자체는 그것을 읽지 않는 쪽에 아무 의무도 지우지 않는다.
- **제어 평면은 mint하는 `logId`에 접두사를 둘 수 있다** (MAY). 어떤 접두사를 두는지는 제어 평면
  데이터 모델의 몫이고 이 문서는 정하지 않는다.
- **그 의미를 전송 평면이 알아야 성립하는 규칙을 만들지 않는다** (MUST NOT). 예를 들어 "이
  접두사의 로그는 append만 되고 pull은 안 된다", "저 접두사는 스코프 검사에서 면제된다" 같은
  규칙은 금지된다 — 그 순간 전송 평면이 접두사를 해석해야 하고, 0002 §1.1이 깨진다.
- 접근 차이는 **접두사가 아니라 스코프로만** 표현된다 (MUST). 접두사는 제어 평면이 자기 기록을
  분류하는 수단이지 인가 수단이 아니다.
- 접두사가 있더라도 §2.1의 예측 불가능성 요구는 그대로다. 접두사는 엔트로피가 아니다.

## 3. 작업공간 토큰

### 3.1 토큰은 작업공간과 같은 사건으로 태어난다

**토큰 발급 라우트를 따로 두지 않는다.** 토큰은 `POST /v1/workspaces`(§4.2)의 응답으로 나오고,
`POST /v1/workspaces/{id}/heartbeat`(§4.3)의 응답으로 갱신된다.

근거:

- 0001 §2.5가 **"토큰은 작업공간 단위로 발급한다"** 고 못박았다. 발급을 별도 라우트로 두면
  *토큰 없는 작업공간*과 *작업공간 없는 토큰*이라는, 계약이 뜻을 부여하지 않은 두 상태가
  표현 가능해진다. 표현할 수 없게 만드는 편이 규칙으로 금지하는 것보다 싸다.
- 갱신을 하트비트와 **같은 사건**으로 두면 "살아 있다고 말하지 않으면 접근이 만료된다"가 구조적으로
  성립한다. 나누면 하트비트는 안 보내면서 갱신만 받는 작업공간 — 서버는 죽었다고 믿는데 계속 쓰고
  있는 작업공간 — 이 표현 가능해지고, 그게 정확히 0001 §2.4가 드러내려던 상태다.
- 대가: 토큰 하나를 여러 작업공간이 공유할 수 없고, 작업공간 하나가 여러 스코프의 토큰을 나눠 들 수
  없다. 지금 요구에는 그런 자리가 없다(런처 하나가 작업공간 하나를 띄운다). 생기면 그때
  `POST /v1/workspaces/{id}/tokens`를 여는 것이 이 계약을 깨지 않고 넓히는 방향이다.

### 3.2 토큰이 싣는 것

토큰은 **자체 검증 가능해야 한다** — 전송 평면이 멤버십·계정 상태를 조회하지 않고 진위와 스코프를
판정할 수 있어야 한다(0002 §1.2, MUST). 그러므로 아래 클레임을 **토큰 자신이 싣는다** (MUST).

| 클레임 | 필수 | 의미 |
|---|---|---|
| `tokenId` | 예 | 이 발급 건의 식별자. 서버 기록·감사 로그가 토큰을 가리키는 **유일한** 방법 (§3.8) |
| `workspaceId` | 예 | 이 토큰이 속한 작업공간 (§4) |
| `audience` | 예 | **`"transport"` 고정.** 전송 평면 전용임을 토큰 자신이 말한다 (§1.1, §3.7) |
| `scope` | 예 | 접근 가능한 `logId`의 배열. **비어 있을 수 없다** (§3.6) |
| `issuedAt` | 예 | 발급 시각 (RFC 3339, UTC) |
| `expiresAt` | 예 | 만료 시각 (RFC 3339, UTC). §3.4의 상한을 지킨다 |
| `keyId` | 예 | 검증 키의 식별자. 회전·긴급 무효화의 단위 (§3.5) |

- **토큰 문자열은 클라이언트에게 불투명하다** (MUST). 클라이언트는 토큰을 파싱하지도, 클레임을
  읽지도, 만료를 스스로 계산하지도 않는다 (MUST NOT). 클라이언트가 알아야 하는 것(`expiresAt`,
  `scope`)은 응답 본문에 **따로** 실린다(§4.2) — 토큰 안을 들여다볼 이유를 남기지 않기 위해서다.
  0002 §1.4가 커서에 대해 세운 규율과 같다.
- **서명 스킴과 검증 키의 배포 형태는 이 문서가 정하지 않는다.** 그 선택은 라이브러리·키 관리·운영
  절차를 함께 끌고 오는 되돌리기 어려운 갈림길이므로, 자리만 비워 두고 `agent:decision`으로
  올린다(§8-1). 이 문서가 정한 것은 그 스킴이 **만족해야 하는 성질**이다:
  1. 전송 평면이 **저장소·계정 테이블을 요청마다 조회하지 않고** 검증할 수 있다 (MUST).
  2. 위 클레임 전체가 **서명에 덮인다** (MUST). 일부만 서명되면 덮이지 않은 클레임이 그대로
     변조 경로다 — 특히 `scope`와 `audience`.
  3. 검증 키는 `keyId`로 식별되고, **키 하나를 무효화하면 그 키로 서명된 토큰이 전부 즉시
     무효가 된다** (MUST). §3.5의 긴급 경로가 여기 걸려 있다.

### 3.3 전송 평면의 검증 절차

전송 평면은 요청마다 아래를 **전부** 통과시킨 뒤에만 진행한다 (MUST). 순서는 자유다.

| # | 검사 | 실패 시 |
|---|---|---|
| 1 | 서명이 알려진 `keyId`의 키로 검증된다 | `401 unauthenticated` |
| 2 | `audience == "transport"` | `401 unauthenticated` |
| 3 | `expiresAt`이 지나지 않았다 (시계 스큐 허용 **≤ 60초**) | `401 unauthenticated` |
| 4 | `scope`가 존재하고, 비어 있지 않고, 해석된다 | `401 unauthenticated` |
| 5 | 요청 경로의 `logId` ∈ `scope` | `403 out_of_scope` |

- 4번이 0002 §1.2의 **fail-closed**다. 스코프가 없거나·비었거나·해석되지 않는 토큰은 **어떤
  로그에 대해서도** 통과할 수 없으므로 자원별 판정(`403`)이 아니라 토큰 자체의 문제이고, 따라서
  `401`이다. 이건 0002를 넓히는 것이 아니라 0002 §1.5의 표(`401` = "검증 실패")를 그대로 적용한
  결과다.
- 3번의 스큐 허용은 **상한이다** (MUST NOT exceed). 짧은 수명으로 폐기를 대신하는 체계에서(§3.5)
  스큐 허용이 크면 폐기 수렴 시간이 그만큼 늘어난다. 60초는 그 손실을 §3.4의 15분 상한 대비 무시할
  수 있는 크기로 잡은 값이다.
- **검증 키 집합을 들고 있는 것은 0002 §1.2가 금지한 "조회"가 아니다.** §1.2가 막은 것은 요청마다
  **주체별 상태**(멤버십·계정)를 보는 것이다. 검증 키는 주체와 무관한 정적 재료이고, 요청 경로의
  `logId`나 주체에 대해 아무 분기도 만들지 않으며, 갱신 빈도가 요청 빈도와 무관하다. 이 구분이
  §3.5의 키 회전이 두 평면 경계를 건드리지 않는 이유다.
- 검증 키를 전송 평면이 **어떻게 받는가**는 배포 사항이다(설정 주입이든 별도 배포 경로든). 다만
  키 배포 실패가 **통과로 떨어지지 않아야 한다** (MUST) — 키를 못 찾으면 `401`이지 통과가 아니다.

### 3.4 수명·갱신

| 파라미터 | 제약 | 근거 |
|---|---|---|
| `tokenTtl` | **≤ 15분** (MUST) | 폐기 수렴 시간의 상한이 곧 이 값이다 (§3.5) |
| `tokenTtl` | **≥ 3 × `heartbeatIntervalSeconds`** (MUST) | 하트비트 한 번 놓쳤다고 토큰이 죽으면 안 된다 |
| `heartbeatIntervalSeconds` | 서버가 응답에 싣는다. 런처는 **그 이하** 주기로 보낸다 (MUST) | 주기를 서버가 쥐어야 grace 계산이 성립한다 (§4.1) |
| `gracePeriod` | **> `tokenTtl`** (MUST) | 접근 상실이 유기 판정보다 **먼저** 와야 한다 — 아래 |

- `gracePeriod > tokenTtl`이 중요한 이유: 유기(`abandoned`) 판정을 받은 작업공간은 그 시점에 이미
  쓸 수 없어야 한다. 판정이 만료보다 먼저 오면 "죽었다고 기록된 작업공간이 계속 밀고 있는" 구간이
  생기고, 그 구간은 조회 결과와 실제가 어긋나는 구간이다.
- **갱신은 하트비트다** (§4.3). 별도 refresh 토큰·refresh 라우트를 두지 않는다 (MUST NOT). 갱신
  자격은 **런처 자격증명**이고, 그것은 샌드박스 밖에 있다.
- 갱신은 **새 `tokenId`를 가진 새 토큰을 발급한다** (MUST). 이전 토큰은 자기 `expiresAt`까지
  유효하다 — 갱신이 이전 토큰을 즉시 죽이면, 갱신 응답이 샌드박스 안으로 전달되는 사이의 요청이
  깨진다.
- **갱신은 스코프를 넓힐 수 없다** (MUST). 갱신 요청에는 스코프 필드가 아예 없으므로(§4.3)
  구조적으로 불가능하고, 그 위에 서버 쪽 의무를 하나 더 둔다: 갱신 시점에 **grant 자격을 다시
  판정한다** (MUST). 자격을 잃은 로그는 스코프에서 빠지고, 빠진 결과가 응답의 `scope`에 그대로
  실린다 (MUST) — 응답이 실제 스코프를 말하지 않으면 그게 조용한 좁힘이다.
- 재판정 결과 스코프가 **전부 비면** 갱신하지 않고 `403 not_grantable`이다 (MUST). 스코프가 빈
  토큰을 만들 수 있는 경로는 존재하지 않는다 (§3.6).
- 개시(§4.2)는 all-or-nothing인데 갱신은 좁혀서 잇는 이유: 개시 시점에는 클라이언트가 아직 아무것도
  하지 않았으므로 전부 거부가 가장 명확하다(부분 성공을 성공으로 오인할 여지가 없다). 갱신 시점에
  전부 거부하면 **아직 자격이 남아 있는 로그로의 flush 경로까지 함께 끊긴다** — 미flush 기억을 잃는
  쪽이 더 나쁘다.

### 3.5 폐기 (revocation)

**자체 검증 가능한 토큰은 정의상 서버가 상태를 보지 않고 통과시키므로, 폐기가 어렵다.** 발급된
토큰은 만료 전까지 살아 있다. 이 문서는 이 긴장을 다음과 같이 정한다.

#### 고른 것: 짧은 수명 + 갱신 거부, 그리고 키 회전을 비상구로

| 경로 | 라우트·수단 | 수렴 시간 | 폭 |
|---|---|---|---|
| **일상 폐기** | `POST /v1/workspaces/{id}/revoke` (§4.5) → 이후 갱신 전부 거부 | **≤ `tokenTtl`** (≤ 15분) | 그 작업공간 하나 |
| **긴급 폐기** | 해당 `keyId`의 검증 키 **즉시 제거** (운영 절차, 라우트 아님) | 즉시 | 그 키로 서명된 **전부** |

- 일상 폐기는 **전송 평면을 전혀 건드리지 않는다.** 폐기는 제어 평면의 기록이고, 전송 평면은
  여전히 아무것도 조회하지 않는다. 폐기가 효력을 갖는 방식은 "다음 갱신이 오지 않는 것"이다.
- **폐기 기록은 응답 전에 내구화된다** (MUST). 아니면 재부팅으로 폐기가 풀린다.
- 긴급 폐기는 **키 회전**이다. §3.2가 요구한 성질 3번(키 하나 무효화 → 그 키의 토큰 전부 무효)이
  이 자리를 위해 있다. 두 가지 회전을 구분한다:
  - **정기 회전**: 새 키로 발급을 옮기고, 이전 키는 **최소 `tokenTtl` 동안 검증만** 유지한다
    (MUST). 겹침 창이 없으면 회전 순간 살아 있는 토큰이 전부 끊긴다.
  - **긴급 회전(kill switch)**: 겹침 없이 즉시 제거한다. 그 키로 발급된 모든 토큰이 그 순간
    `401`이 된다. 대가는 폭이다 — 사고와 무관한 작업공간도 함께 끊긴다. 런처는 새 작업공간을 열어
    이어간다(§4.7의 `supersedes`).

#### 채택하지 않은 것: 전송 평면의 폐기 목록

전송 평면이 폐기 목록(denylist)을 보게 하면 즉시·세밀한 폐기가 가능하다. **채택하지 않는다.**

- 그 순간 전송 평면이 요청마다 **주체별 상태**를 조회하게 되고, 그것이 0002 §1.2가 금지한 바로
  그것이다. 목록이 "계정 테이블"이 아니라는 말은 형식적 방어에 불과하다 — 요청마다 외부 상태를
  봐야 통과 여부가 갈린다는 성질이 같고, 그 성질이 두 평면 경계를 무너뜨린다(0001 §1.4).
- 더 실제적인 문제: 목록 조회가 전송 평면의 append 경로에 들어가면, 그 조회의 가용성이 곧 push의
  가용성이 된다. push 성공이 "이 작업공간을 죽여도 된다"의 유일한 근거인 설계에서(0001 §2.2,
  0002 §2.2) 그건 내구성 경로에 새 단일 장애점을 세우는 것이다.

#### 어디까지 양보했는가

**양보한 것은 즉시성이지 경계가 아니다.** 좁은 폐기의 수렴 시간이 0이 아니라 `tokenTtl`(≤ 15분)
이고, 0으로 만들려면 폭이 넓은 키 회전을 써야 한다. 이 두 축 사이에 "즉시 + 좁게"는 없다.

그 대가를 감수하는 이유는 폐기 대상이 **작업공간**이기 때문이다. 작업공간은 수 분에서 수십 분 사는
임시 실행 단위이고(0001 §2.4), 15분은 그 수명과 같은 자릿수다. 사람 계정처럼 몇 달 사는 주체를
폐기하는 문제였다면 이 선택은 틀렸을 것이다.

**재검토 조건**(§8-7): 작업공간 수명이 시간 단위로 길어지거나, "즉시 + 좁게"가 필요한 실제 사고가
한 번이라도 생기면 이 절을 다시 연다.

### 3.6 스코프 fail-closed는 발급 쪽에서도 유지된다

0002 §1.2는 **판정** 쪽에서 fail-closed를 요구했다(스코프가 없거나·비었거나·해석 불가면 전부 거부).
발급 쪽에서 그것을 깨지 않으려면, **스코프가 빈 토큰을 만들 수 있는 경로가 없어야 한다.**

- **`POST /v1/workspaces`의 `logs`는 필수이고 길이 ≥ 1이다** (MUST). 없거나 빈 배열이면
  `400 empty_scope`. 빈 스코프로 작업공간을 여는 것은 이 계약에 존재하지 않는다.
- **발급된 토큰의 `scope`는 요청한 `logs`와 같다** (MUST). 서버가 더 넓게 발급하지 않고, 조용히
  좁히지도 않는다.
- 요청한 로그 중 **하나라도** 이 주체가 grant할 수 없으면 **전부 거부**한다 —
  `403 not_grantable`, 작업공간은 만들어지지 않는다 (MUST). `details.logIds`에 거부된 id를 싣는다.
  조용히 좁혀서 발급하면 클라이언트는 자기가 요청한 스코프를 얻었다고 믿는다. 0002 §2.1의
  all-or-nothing 검증과 같은 규율이다.
- **grant 판정 자체는 반드시 일어난다** (MUST). 그 판정의 **규칙**(어떤 주체가 어떤 로그를 grant할
  수 있는가)은 계정·멤버십 모델의 몫이고 이 문서의 범위가 아니다(§8-3). 계약으로 남는 것은
  "판정이 발급 시점에 일어난다"와 "실패 시 `403 not_grantable`"이다.
- 갱신 시에도 스코프가 빈 토큰은 나오지 않는다 (§3.4).
- **스코프 판정을 끄는 배포 스위치를 두지 않는다** (MUST NOT). "로컬이니까", "개발 환경이니까"로
  검사를 건너뛰는 경로가 하나라도 있으면 그 경로가 곧 유출 경로다. 로컬 데몬이어도 같다(§7.1).

### 3.7 샌드박스 안에서는 권한이 넓어지지 않는다

0001 §2.5: *"신뢰 결정은 샌드박스 밖에 있어야 한다."* 이 문서에서 그것이 조항으로 읽히는 자리는
셋이고, **세 개가 겹쳐야** 성립한다.

1. **작업공간 토큰은 제어 평면에서 주체가 아니다** (MUST). `audience == "transport"`인 토큰으로
   이 문서의 어떤 라우트를 호출해도 `401 unauthenticated`다. 즉 **에이전트는 발급 라우트에 들어갈
   수 없다.** 스코프를 넓힌 새 토큰을 요청하는 것 이전에, 요청하는 행위 자체가 성립하지 않는다.
2. **갱신은 스코프를 넓힐 수 없다** (§3.4). 설령 런처 자격증명이 샌드박스 안으로 새어 들어가도,
   갱신 경로로는 이미 가진 것보다 넓어질 수 없다.
3. **로그 생성도 런처의 행위다** (§2.1, 런처 자격증명 필요). 에이전트가 새 로그를 만들어 자기
   스코프에 얹는 경로가 없다.

우회 경로를 막는 조항도 함께 둔다:

- **작업공간 토큰을 제어 평면 자격으로 교환하는 경로를 두지 않는다** (MUST NOT). 토큰 교환·승격·
  `impersonate` 류 라우트는 이 문서에 없고, 추가하지 않는다.
- **검사 대상이 0건일 때를 통과로 처리하지 않는다** (MUST NOT). 스코프가 빈 토큰(§3.6), `logs`가
  빈 요청(§3.6), 스코프에 없는 로그(§3.3-5) — 셋 다 거부다. "검사할 게 없으니 통과"는 이 종류
  검사의 전형적인 실패 방식이다.

### 3.8 토큰 값이 남는 곳은 응답 본문 하나뿐이다

- **서버는 발급한 토큰 문자열을 저장하지 않는다** (MUST NOT). 서버가 기록하는 것은 `tokenId`·
  `keyId`·`workspaceId`·스코프·발급/만료 시각이다. 저장된 토큰은 그 자체로 유출 자산이고,
  §3.5의 폐기 설계는 토큰을 보관할 것을 요구하지 않는다.
- **토큰 값은 응답 본문 이외 어디에도 실리지 않는다** (MUST NOT): 서버 로그, 액세스 로그, 감사
  기록, 에러 `message`·`details`, 메트릭 라벨, 조회 응답(§4.6) — 전부 포함이다. 감사 기록이
  토큰을 가리켜야 하면 `tokenId`를 쓴다.
- 조회 라우트(§4.6)는 **어떤 경우에도 토큰을 돌려주지 않는다** (MUST NOT). 토큰을 다시 얻는 방법은
  갱신(§4.3)뿐이고, 그건 새 토큰을 발급하는 것이지 이전 것을 되읽는 것이 아니다.
- 0002 §1.2의 마지막 줄(토큰 값은 응답 본문·에러 메시지·서버 로그 어디에도 실리지 않는다)이
  전송 평면에서 요구한 것과 같은 규율이고, 발급하는 쪽이 지키지 않으면 판정하는 쪽이 지켜도
  소용이 없다.

## 4. 작업공간 생애 추적

0001 §2.4가 요구한 것: *"작업공간 생성·활성·종료를 서버가 안다. 그래야 'flush 없이 죽은 작업공간'이
조용히 사라지지 않고 드러난다."*

### 4.1 상태

```
                    ┌── close{outcome:"flushed"}   ──► closed_flushed
                    │
   (개시) ──► active ├── close{outcome:"discarded"} ──► closed_discarded
                    │
                    ├── revoke                     ──► revoked
                    │
                    └── lastHeartbeatAt + gracePeriod 경과 ──► abandoned
```

| 상태 | 뜻 |
|---|---|
| `active` | 살아 있다. 하트비트가 grace 창 안에 있다 |
| `closed_flushed` | 하네스가 **flush를 마쳤다고 선언하고** 닫았다. 정상 종료 |
| `closed_discarded` | 하네스가 **의도적으로 버리고** 닫았다. 정상 종료지만 기억은 남지 않았다 |
| `revoked` | 폐기됐다 (§3.5) |
| `abandoned` | **아무 선언 없이 하트비트가 끊겼다.** 이것이 "flush 없이 죽은 작업공간"이다 (§4.7) |

- **`active`를 제외한 네 상태는 모두 종단이다** (MUST). 종단 상태의 작업공간에 대한 하트비트·종료
  선언은 `409 workspace_not_active`다.
- **`abandoned`에서 부활하지 않는다** (MUST NOT). 늦게 도착한 하트비트로 `active`로 되돌리면,
  유기 판정을 받았던 작업공간이 조회 결과에서 조용히 사라진다 — 0001 §2.4가 막으려던 것이 정확히
  그 소실이다. 대신 런처는 새 작업공간을 열고 `supersedes`로 잇는다(§4.2, §4.7).
- 대가: `gracePeriod`보다 긴 네트워크 단절을 만난 **살아 있는** 작업공간이 유기로 판정된다.
  그 작업공간은 토큰이 이미 만료돼(`gracePeriod > tokenTtl`) 밀 수 없으므로, 하네스는 새 작업공간을
  열어 미flush 기억을 다시 민다. 이벤트 `id` 기준 dedup(0002 §2.4)이 그 재밀기를 안전하게 만든다.
  `gracePeriod`를 짧게 잡을수록 이 오탐이 늘고, 길게 잡을수록 진짜 죽은 작업공간의 발견이 늦는다.
  값은 배포 파라미터이고 이 문서는 `gracePeriod > tokenTtl`만 요구한다(§3.4).

#### 내구성과 원자성

- **`active`·`closed_*`·`revoked`로의 전이는 응답 전에 내구화된다** (MUST). 보장할 수 없으면
  `503 not_durable`이다. 작업공간 기록이 재부팅에 살아남지 않으면 유기 판정도 함께 사라지고,
  그건 §4.7의 관찰 조건이 통째로 무너지는 것이다. 0002 §2.2가 이벤트에 대해 세운 것과 같은 층위다.
- **작업공간 기록의 내구화가 토큰 발급(응답 전송)보다 먼저다** (MUST). 순서가 뒤집히면 재부팅 후
  서버가 모르는 토큰이 살아 있게 되고 — 스코프가 유효하므로 그 토큰은 쓸 수 있다 — 그 작업공간은
  추적에서 조용히 빠진다.
- **하트비트 시각의 갱신은 내구성 요구에서 제외한다** (MAY 지연 기록). 하트비트마다 fsync를
  요구하면 비용이 주기에 비례해 붙는데, 하트비트 유실은 유기 **오탐** 쪽으로 기울고 그 방향은
  안전하다(드러나는 쪽이다). 반대 방향으로 기우는 전이(§4.4·§4.5)만 내구성을 요구한다.
- **상태 읽기·전이·기록은 원자적이다** (MUST). 같은 작업공간에 대한 `close`와 하트비트가 동시에
  도착해도 결과는 둘 중 하나이지, "닫힌 뒤 하트비트가 `active`로 되돌리는" 것이 아니다.
- **토큰 발급은 상태 판정과 원자적이다** (MUST). 상태를 `active`로 읽은 뒤 토큰을 서명해 응답하는
  사이에 `revoke`(§4.5)나 `close`(§4.4)가 확정되면, **폐기된 작업공간에 새 토큰이 나간다** — 그
  토큰은 `tokenTtl` 동안 유효하므로 §3.5가 약속한 폐기 수렴 시간이 그만큼 늘어난다. 폐기가 이
  체계의 유일한 좁은 폐기 수단이므로(§3.5) 이 경합을 열어 두면 폐기 계약 자체가 확률적이 된다.

#### 유기 판정은 조회 시점에 계산한다

**`abandoned` 판정은 조회 시점에 `lastHeartbeatAt + gracePeriod`로 계산한다** (MUST). 별도 스케줄러·
배치 작업이 돌아야만 상태가 바뀌는 구현을 금지한다 (MUST NOT).

근거: 배치에 의존하면 배치가 죽었을 때 유기 작업공간이 **영원히 `active`로 보인다.** 조회는
`abandoned` 0건을 돌려주고, 그건 "유기된 작업공간이 없다"와 구별되지 않는다 — 검사가 돌지 않는 것이
합격으로 보이는 형태다.

하트비트가 도착했을 때 서버는 **먼저 파생 상태를 계산하고**, 이미 유기면 `abandoned`를 기록으로
확정한 뒤 `409 workspace_not_active`를 돌려준다 (MUST). 이것이 파생 상태와 종단성(부활 금지)을
동시에 지키는 자리다.

### 4.2 개시 — `POST /v1/workspaces`

```
POST /v1/workspaces
Authorization: Bearer <런처 자격증명>
Content-Type: application/json
Idempotency-Key: <키>
```

```ts
type OpenWorkspaceRequest = {
  logs: string[]        // 길이 ≥ 1. 각 원소는 0002 §1.1의 logId 정규식
  supersedes?: string   // 이어받는 이전 workspaceId (§4.7). 서버는 검증하지 않는다
}
```

```ts
type OpenWorkspaceResponse = {
  workspaceId: string
  token: string                     // 이 응답에만 실린다 (§3.8)
  tokenId: string
  scope: string[]                   // == 요청의 logs (§3.6)
  expiresAt: string                 // RFC 3339 UTC
  heartbeatIntervalSeconds: number  // 런처는 이 이하 주기로 하트비트를 보낸다 (§3.4)
}
```

성공 상태코드: **`201 Created`**.

| 실패 | 상태 | `code` |
|---|---|---|
| `logs` 없음·빈 배열 | `400` | `empty_scope` |
| `logs` 원소가 정규식 위반 | `400` | `invalid_log_id` |
| `workspaceId`를 제안 | `400` | `client_minted_id` |
| `Idempotency-Key` 없음 | `400` | `missing_idempotency_key` |
| grant 불가한 로그가 하나라도 있음 | `403` | `not_grantable` (`details.logIds`) |
| `supersedes`가 없는 / 다른 주체의 작업공간 | `404` | `workspace_not_found` |
| 같은 키·다른 본문 | `409` | `idempotency_key_reused` |
| 종단 상태(§4.1)의 작업공간에 대한 멱등 재시도 | `409` | `workspace_not_active` (`details.workspaceId`, `details.state`) |

- `workspaceId`도 **서버가 mint한다** (MUST). §2.1·§2.2의 규칙(예측 불가 성분, 클라이언트 제안
  금지)이 그대로 적용된다.
- **`lastHeartbeatAt`은 개시 시 `openedAt`으로 초기화된다** (MUST). 하트비트를 한 번도 보내지
  못하고 죽은 작업공간 — 개시 직후 크래시 — 도 이 값을 갖는다. §4.1의 유기 판정과 §4.6의
  `endedAt`이 **둘 다 `lastHeartbeatAt`을 근거로 삼으므로**, 초기값이 없으면 그 케이스가 파생 상태
  계산에서 통째로 빠진다. 그런데 그것이 §4.7이 드러내려는 것의 가장 흔한 모양이다.
- **멱등 재시도는 같은 `workspaceId`를 돌려주되 토큰은 새로 발급한다** (MUST). 이유: 재시도 응답에
  같은 토큰을 실으려면 서버가 토큰 문자열을 보관해야 하고, 그건 §3.8이 금지한다. 새 토큰은 같은
  스코프·같은 작업공간이므로 권한이 넓어지지 않고, 이전 토큰은 자기 만료까지 유효하다.
  **`token`·`tokenId`·`expiresAt`을 제외한 응답 필드는 첫 응답과 같다** (MUST).
  - `expiresAt`이 제외에 드는 이유: 새 토큰은 발급 시점 기준의 새 만료를 갖는다(§3.4). 첫 응답
    값으로 고정하면 재시도가 늦을수록 **이미 지난 시각**이 나가고, §3.2가 토큰 파싱을 금지한
    이상 클라이언트에게 이 필드가 만료를 아는 유일한 근거이므로 **막 받은 유효한 토큰을 만료된
    것으로 읽는다.** §3.2가 "토큰 안을 들여다볼 이유를 남기지 않는다"고 정한 설계가 성립하려면
    응답 본문이 실제 토큰을 말해야 한다.
- **작업공간이 이미 종단 상태(§4.1)면 멱등 재시도는 `409 workspace_not_active`다** (MUST). 첫
  결과를 돌려주지 않는다 — §1.4의 "첫 결과를 그대로"에 대한 예외이고 §1.4에도 적혀 있다.
  - 근거: 멱등 재시도는 **갱신이라는 이름을 쓰지 않는 별도의 발급 경로**다. 개시 응답이 유실되고,
    운영자가 그 작업공간을 `revoke`(§4.5)한 뒤, 런처가 같은 키로 재시도하는 인터리브를 생각하라.
    이 거부가 없으면 **폐기된 작업공간에 `tokenTtl`짜리 새 토큰이 나가고**, §3.5가 약속한 수렴
    시간 ≤ `tokenTtl`이 이 경로에서 성립하지 않는다. §4.1이 *한 요청 안에서* 닫은 경합을 재시도
    경로에서 다시 여는 셈이다. 발급은 언제나 상태 판정을 통과해야 한다.
  - **이 `409`의 `details`에 `workspaceId`와 `state`를 싣는다** (MUST). 응답을 잃은 런처는 자기가
    무엇을 열었는지 모르므로, 이것이 없으면 새 작업공간을 열 때 `supersedes`(§4.7)로 이을 수
    없다 — §4.7이 드러내려는 이어받음 관계가 정확히 이 경로에서 끊긴다. 열거 오라클이 아니다:
    같은 주체가 자기 멱등성 키로 자기가 만든 자원을 되묻는 것이고, 키를 모르면 아무것도 나오지
    않는다.
- `supersedes`가 가리키는 것이 **미flush분을 실제로 이어받았는지**는 서버가 판정할 수 없다
  (§4.8). 그건 선언이고, 서버는 기록해 두고 조회에서 보여줄 뿐이다.
- 다만 **`supersedes`는 같은 주체의 작업공간이어야 한다** (MUST). 아니면(없는 id이거나 다른
  주체의 것이거나) `404 workspace_not_found`이고 작업공간은 만들어지지 않는다. 이 검증까지
  빼면 아무나 남의 작업공간에 `supersededBy`를 붙일 수 있고, 그건 **남의 유기 기록을 "누가
  이어받았다"로 덮는** 것이다 — §4.7이 드러내려는 바로 그 신호를 지우는 쓰기다. "이어받음이
  사실인가"는 검증할 수 없지만 "쓰는 사람이 그 기록의 주인인가"는 검증할 수 있고, 해야 한다.

### 4.3 하트비트 — `POST /v1/workspaces/{workspaceId}/heartbeat`

```
POST /v1/workspaces/{workspaceId}/heartbeat
Authorization: Bearer <런처 자격증명>
Content-Type: application/json
```

```ts
type HeartbeatRequest = Record<string, never>   // {} — 정의된 필드가 없다
```

```ts
type HeartbeatResponse = {
  workspaceId: string
  state: "active"
  token: string                     // 갱신된 토큰. 새 tokenId (§3.4)
  tokenId: string
  scope: string[]                   // 재판정 결과. 좁아졌으면 좁아진 채로 실린다 (§3.4)
  expiresAt: string
  heartbeatIntervalSeconds: number
}
```

성공 상태코드: **`200 OK`**.

| 실패 | 상태 | `code` |
|---|---|---|
| 없는 작업공간 / 다른 주체의 것 | `404` | `workspace_not_found` |
| 종단 상태 (`closed_*`·`revoked`·`abandoned`) | `409` | `workspace_not_active` |
| 재판정 결과 스코프가 전부 빔 | `403` | `not_grantable` |

- **요청 본문에 스코프 필드가 없다.** 갱신이 스코프를 넓힐 수 없다는 것을 규칙이 아니라 구조로
  만든다 (§3.4, §3.7).
- 하트비트는 **그 자체로 멱등이다** — 여러 번 보내도 `lastHeartbeatAt`이 앞으로 갈 뿐이다. 다만
  매번 새 토큰이 발급되므로, 런처는 필요 이상으로 자주 보내지 않는다.
- 이 라우트는 **런처의 의무**다. 샌드박스 안의 에이전트는 런처 자격증명을 갖지 않으므로 자기
  작업공간의 하트비트를 스스로 보낼 수 없다 (§3.7). 그래서 "에이전트가 죽었는데 하트비트는 계속
  가는" 상태가 생기지 않는다 — 하트비트를 보내는 쪽이 작업공간을 만들고 지우는 쪽과 같다
  (0001 §2.4: *"작업공간을 만들고 지우는 주체는 하네스다"*).

### 4.4 종료 선언 — `POST /v1/workspaces/{workspaceId}/close`

```
POST /v1/workspaces/{workspaceId}/close
Authorization: Bearer <런처 자격증명>
Content-Type: application/json
```

```ts
type CloseWorkspaceRequest = {
  outcome: "flushed" | "discarded"
}
```

```ts
type CloseWorkspaceResponse = {
  workspaceId: string
  state: "closed_flushed" | "closed_discarded"
  endedAt: string   // RFC 3339 UTC
}
```

성공 상태코드: **`200 OK`**.

| 실패 | 상태 | `code` |
|---|---|---|
| 없는 작업공간 / 다른 주체의 것 | `404` | `workspace_not_found` |
| 이미 **다른** outcome으로 닫힘, 또는 `revoked`·`abandoned` | `409` | `workspace_not_active` |
| `outcome` 없음·두 값 밖 | `400` | `malformed_request` |

- **같은 `outcome`으로 다시 닫으면 `200`이고 본문이 같다** (MUST). 재시도가 안전해야 하므로 이
  라우트는 멱등성 키 없이 멱등이다.
- `outcome`을 선택 필드로 두지 않은 이유: 기본값을 두면 하네스가 아무 생각 없이 닫은 것과 flush를
  마치고 닫은 것이 같은 기록을 남긴다. **선언은 명시적이어야 기록으로서 값이 있다.**
- `discarded`를 둔 이유: 하네스가 기억을 남기지 않기로 하고 작업공간을 버리는 것은 정상 경로다
  (작업 실패, 실험, 폐기된 브랜치). 그것과 §4.7의 유기를 같은 기록으로 만들면 진짜 사고가 정상
  운영에 묻힌다.
- **닫아도 이미 발급된 토큰은 자기 만료까지 유효하다** (§3.4의 대가). 닫은 뒤 최대 `tokenTtl`
  동안은 그 토큰으로 밀 수 있다. 해로운 상태는 아니다 — 스코프가 같고, 그 로그는 어차피 그
  작업공간의 것이다. 대가를 없애려면 전송 평면이 작업공간 상태를 조회해야 하고, 그건 §3.5가
  채택하지 않은 것이다.
- **닫은 뒤 잔여 토큰 창의 상한은 `tokenTtl`(≤ 15분)이고, `close` 뒤에 부를 수 있는 라우트로
  그것을 줄이는 방법은 없다.** `revoke`(§4.5)는 여기서 쓸 수 없고 쓸 이유도 없다 — `closed_*`에
  대한 폐기는 `409 workspace_not_active`이며(§4.5), 설령 순서를 뒤집어 먼저 불렀더라도 폐기의
  효력은 *이후 갱신 거부*이지 즉시 무효화가 아니다(§3.5). **잔여 창을 0으로 만드는 유일한 수단은
  §3.5의 긴급 키 회전이고, 그 대가는 폭이다** — 그 키로 서명된 무관한 작업공간까지 함께 끊긴다.
  §3.5가 세운 "즉시 + 좁게는 없다"가 이 자리에도 그대로 적용된다.

### 4.5 폐기 — `POST /v1/workspaces/{workspaceId}/revoke`

```
POST /v1/workspaces/{workspaceId}/revoke
Authorization: Bearer <런처 자격증명>
Content-Type: application/json
```

```ts
type RevokeWorkspaceRequest = {
  reason?: string   // 사람이 읽는 설명. 자격증명·payload 원문을 담지 않는다 (§3.8)
}
```

```ts
type RevokeWorkspaceResponse = {
  workspaceId: string
  state: "revoked"
  endedAt: string
}
```

성공 상태코드: **`200 OK`**. 이미 `revoked`면 같은 `200`과 같은 본문이다 (멱등, MUST).
`closed_*`·`abandoned`인 작업공간에 대한 폐기는 `409 workspace_not_active`다 — 이미 갱신되지 않는
상태이므로 폐기가 더할 것이 없다.

효력은 §3.5 그대로다: **이후 갱신이 전부 거부된다.** 이미 발급된 토큰은 만료까지 유효하고, 그
잔여 창의 상한이 `tokenTtl`(≤ 15분)이다.

### 4.6 조회 — `GET /v1/workspaces`, `GET /v1/workspaces/{workspaceId}`

```
GET /v1/workspaces?state=<state>&after=<cursor>&limit=<n>
Authorization: Bearer <런처 자격증명>
```

| 쿼리 | 필수 | 의미 |
|---|---|---|
| `state` | 아니오 | §4.1의 상태 이름 하나. 없으면 상태로 거르지 않는다 |
| `after` | 아니오 | 서버 발급 불투명 커서. 이 커서 **다음**부터 |
| `limit` | 아니오 | 이 응답에 실을 최대 건수. 서버가 더 작게 깎을 수 있다 |

```ts
type WorkspaceRecord = {
  workspaceId: string
  state: "active" | "closed_flushed" | "closed_discarded" | "revoked" | "abandoned"
  logs: string[]            // 개시 시 스코프 (§4.2의 요청 logs)
  openedAt: string          // RFC 3339 UTC
  lastHeartbeatAt: string   // 개시 시 openedAt으로 초기화된다 (§4.2)
  endedAt?: string          // 종단 상태에서만
  supersedes?: string
  supersededBy?: string
}

type ListWorkspacesResponse = {
  workspaces: WorkspaceRecord[]
  cursor?: string    // workspaces의 마지막 항목 커서. 비면 없음
  hasMore: boolean
}
```

성공 상태코드: **`200 OK`**. 빈 결과도 `200`이다.

`GET /v1/workspaces/{workspaceId}`는 단건 `WorkspaceRecord`를 `200`으로 돌려준다. 없거나 다른
주체의 것이면 `404 workspace_not_found`(§1.3).

규칙:

- **주체 스코프는 필터가 아니다** (MUST). 응답에는 **요청 주체가 연 작업공간만** 실린다. 이것을
  끄거나 다른 주체를 지정하는 쿼리 파라미터는 없다 (MUST NOT) — 있으면 그게 곧 열거 경로다.
- **`state` 값이 §4.1의 이름 중 하나가 아니면 `400 invalid_state_filter`다** (MUST). 빈 문자열·
  알 수 없는 값·타입 불일치를 "필터 없음"으로 떨어뜨리지 않는다 (MUST NOT). 필터가 조용히 꺼지면
  호출자는 좁게 물었다고 믿으면서 전부를 받는다.
- **적용 순서는 필터 → 정렬 → `limit`이다** (MUST). 정렬은 `openedAt` **오름차순**(오래된 것부터)
  이고, 같은 값이면 `workspaceId` 사전순으로 안정화한다.
  - `limit`을 필터보다 먼저 걸면 유기 작업공간이 최신 항목들에 밀려 조회 결과에서 사라진다.
  - 최신순으로 자르면 더 나쁘다 — **유기 작업공간은 정의상 오래된 항목**이므로, 정확히 봐야 할
    것이 먼저 잘려나간다. 0002 §3.1이 pull의 `limit`에 대해 세운 규율과 같은 이유다.
- `limit`은 페이지 크기일 뿐 필터가 아니다. 잘려나간 항목은 사라지지 않고 다음 페이지에 있다.
- `after`가 해석되지 않으면 `400 invalid_cursor`다 (MUST). 전송 평면의 "미지 커서 → 전량 반환"
  (0002 §3.2)을 여기로 옮기지 않는다 — 그 규칙은 이벤트를 놓치면 안 되는 append-only 로그의
  것이고, 여기서는 조용히 처음부터 주는 것보다 명시적 오류가 호출자에게 정확하다. **어느 쪽이든
  "조용히 head부터"는 금지**라는 관통 규칙(0002 §3.2)은 그대로다.
- **응답에 토큰이 실리지 않는다** (MUST NOT) — §3.8.
- `logs`는 **개시 시 스코프**다. 갱신으로 좁아진 현재 스코프(§3.4)는 조회에 싣지 않는다 — 이
  라우트가 답해야 하는 질문은 "이 작업공간이 **무엇을 밀고 있었나**"이고(§4.7), 그 답은 개시 시
  스코프다. 현재 스코프는 갱신 응답이 그때그때 말한다(§4.3).
- **`abandoned`의 `endedAt`은 `lastHeartbeatAt + gracePeriod`다** (MUST). 조회 시각이 아니다 —
  조회 시각을 쓰면 같은 기록이 조회할 때마다 다른 `endedAt`을 보이고, 그러면 그 필드로 사고
  시점을 되짚을 수 없다. 파생 상태여도 값은 결정적이어야 한다(§4.1).

### 4.7 "flush 없이 죽은 작업공간"은 이렇게 보인다

0001 §2.4가 요구한 가시성의 **관찰 조건**을 적는다. 0002 §2.2가 내구성을 `kill -9` 시험으로 적은
것과 같은 층위다 — *무엇을 조회하면 그 상태가 보이는가*.

> 런처가 작업공간을 열고(§4.2), 하트비트를 몇 번 보낸 뒤(§4.3), `close`를 부르지 않고 프로세스를
> `kill -9` 한다. `lastHeartbeatAt + gracePeriod`가 지난 뒤
> `GET /v1/workspaces?state=abandoned`를 호출하면, 그 `workspaceId`가 응답에 있고
> `state`는 `"abandoned"`, `endedAt`은 `lastHeartbeatAt + gracePeriod`이며, `logs`에 그 작업공간이 밀고 있던
> 로그가 그대로 실려 있다.

이 시험이 성립하기 위해 필요한 조항은 전부 앞에 있다:

| 필요한 것 | 조항 |
|---|---|
| 서버가 작업공간의 존재를 안다 | §4.2 개시 라우트 + 기록 내구화 (§4.1) |
| 서버가 "살아 있음"을 안다 | §4.3 하트비트, 주기는 서버가 쥔다 (§3.4) |
| 정상 종료와 구별된다 | §4.4 `close`의 명시적 `outcome` |
| 배치가 죽어도 드러난다 | §4.1 유기 판정을 **조회 시점에** 계산 |
| 조용히 사라지지 않는다 | §4.1 `abandoned`는 종단, 부활 금지 |
| 오래된 항목이 잘리지 않는다 | §4.6 필터 → 정렬(오래된 것부터) → `limit` |

**이어받음(`supersedes`)**: 유기가 항상 사고인 것은 아니다 — `gracePeriod`보다 긴 단절, 긴급 키
회전(§3.5)도 유기를 만든다. 런처가 새 작업공간을 열며 `supersedes: <이전 workspaceId>`를 실으면,
이전 작업공간의 조회 결과에 `supersededBy`가 붙는다. 그래서 조회자는 **아무도 이어받지 않은 유기**와
**이어받은 유기**를 구분할 수 있다. 서버는 이 선언을 검증하지 않는다(§4.8) — 검증할 수 없기 때문이고,
검증하는 척하는 것보다 선언임을 명시하는 편이 정직하다.

### 4.8 서버가 검증할 수 없는 것

**서버는 flush가 실제로 일어났는지 판정할 수 없다.** 구조적으로 그렇다:

- payload는 불투명하고(0002 §1.3), 서버는 클라이언트의 로컬 db에 무엇이 있었는지 모른다. "밀어야
  했던 것"의 집합이 서버에 없으므로 "다 밀었는가"는 서버가 답할 수 있는 질문이 아니다.
- 그러므로 `close{outcome:"flushed"}`는 **선언**이지 증명이 아니다. `supersedes`도 마찬가지다.

**서버가 하는 일은 선언의 부재를 드러내는 것이다.** 0001 §2.4가 요구한 것이 정확히 그 층위다 —
*"flush 보장도 하네스의 몫이다. 서버는 그것이 지켜졌는지 **보이게** 해야 한다."* 보장이 아니라
가시성이다.

거짓 선언(밀지 않고 `flushed`로 닫기)은 이 계약이 막지 못한다. 막으려면 서버가 클라이언트 상태를
알아야 하고, 그건 payload 불투명성(0001 §1.1)과 정면으로 부딪힌다. 이 한계는 계약의 결함이 아니라
경계다.

## 5. 0002 §5 불변식 대조표 4번을 닫는다

0002 §5는 0001 §1의 네 불변식 중 **4번(두 평면 경계 — 전송/제어 분리, 식별자는 서버 발급)** 을
`부분`으로 남겼다. 표현되지 않은 쪽이 **식별자 발급(server-minted) 자체**였고, 그것이 이 문서의
몫이다.

0001 §1.4를 두 요구로 쪼개어 1:1로 짚는다.

| 4번이 요구한 것 | 표현됐는가 | 조항 |
|---|---|---|
| **전송(dumb)/제어(smart) 분리** | 예 | **0002 쪽**: §1.1 전송 평면은 prefix-blind / §1.2 멤버십·계정 미조회 + 스코프 강제 + fail-closed / §7.2 잠금·CAS 없음 / §0 라우트 셋 고정. **이 문서 쪽**: §0 제어 평면은 이벤트·커서를 다루지 않는다 / §1.1 두 자격이 서로의 평면에서 통하지 않는다 / §2.3 접두사 의미는 제어 평면 안에 머문다 / §3.3 전송 평면의 검증이 조회 없이 끝난다 / §3.5 폐기가 전송 평면을 건드리지 않는다 / §7.2 조정을 제어 평면으로 끌어오지 않는다 |
| **식별자는 서버가 발급한다 (server-minted)** | 예 | **이 문서 §2.1** — `POST /v1/logs`가 `logId`를 mint하는 유일한 경로다. **§2.2** — 클라이언트의 제안을 `400 client_minted_id`로 거부하고, 조용히 무시하지 않는다. **§4.2** — `workspaceId`도 같은 규칙으로 서버가 mint한다. 전송 평면에는 로그를 만드는 경로가 아예 없다(0002 §0의 라우트 셋 고정) |

**결론: 0002 §5의 4번은 `부분` → `예`다.**

- 0002 §5.4의 "부분인 이유" 절은 *"빠진 것은 이 문서가 다룰 수 없는 것이지, 누락이 아니다"* 라고
  적었다. 그 빠진 것이 위 표의 두 번째 행으로 채워졌다.
- **0002를 수정하지 않는다.** 0002는 머지된 계약이고, 그 문서의 표에 적힌 `부분`은 *0002 시점의*
  사실로서 여전히 맞다. 4번이 두 문서에 걸쳐 닫혔다는 사실은 이 절이 기록한다.

## 7. 이 문서가 전제하지 않는 것

### 7.1 로컬 데몬의 유무 (0001 §4.1 미결)

**이 스펙은 데몬이 있든 없든 동일하다.** 0002 §7.1이 세운 시험 — *"결정되더라도 이 문서는 바뀌지
않아야 한다"* — 을 이 문서도 통과해야 한다. 토큰을 어디에 두는가가 데몬 유무에 따라 달라 보일 수
있으므로 여기가 새기 쉬운 자리다.

구체적으로 지킨 것:

- **제어 평면 베이스 URL은 런처가 주입한다**(§1.1). `localhost`·유닉스 소켓·특정 포트·특정 호스트를
  이 문서가 정하지 않는다. 제어 평면 라우트를 로컬 데몬이 서비스하든 원격 hub가 서비스하든 런처
  코드는 같다.
- **토큰의 저장 위치·전달 수단을 정하지 않는다.** 이 문서가 정한 것은 "런처가 발급받아 작업공간에
  주입한다"(0001 §2.5)까지다. 환경변수인지, 파일인지, 소켓으로 건네는지는 런처·클라이언트 사항이고
  데몬 결정에 따라 달라져도 이 문서는 바뀌지 않는다.
- **"로컬이니까 인증을 생략한다"는 예외가 없다**(§3.6). 0002 §7.1이 전송 평면에서 같은 예외를 두지
  않은 것과 같다.
- **`heartbeatIntervalSeconds`·`gracePeriod`·`tokenTtl`은 배포 파라미터다**(§3.4). 데몬은 짧게,
  원격 hub는 길게 잡을 수 있고 그 차이가 계약을 바꾸지 않는다.
- 이 문서는 제어 평면을 **누가 서비스하는지** 말하지 않는다. "서버"는 이 여섯 라우트를 서비스하는
  무엇이다.

**데몬을 둘 것인가는 이 문서가 결정하지 않는다.** 결정되더라도 이 문서는 바뀌지 않아야 한다.
바뀌어야 한다면 그건 데몬 전제가 새어 들어갔다는 신호다.

### 7.2 조정(mutual exclusion)은 여기에도 없다

0002 §7.2가 전송 평면에서 조정을 배제했다. **제어 평면이라고 끌어들이지 않는다.** 0001 §4.2가 정한
것은 *"같은 자리에 두지 않는다"* 까지다.

하트비트(§4.3)가 리스처럼 **보이므로** 명시적으로 부인한다:

- **하트비트는 작업공간의 생존 신호이지, 자원에 대한 리스가 아니다** (MUST). 하트비트를 보내고
  있다는 사실이 어떤 로그에 대해서도 배타적 권리를 주지 않는다.
- **여러 작업공간이 같은 로그를 동시에 열 수 있다** (MUST 허용). 서버는 그것을 거부하지 않고,
  경고하지도, 순서를 정하지도 않는다. 두 작업공간이 같은 로그에 동시에 밀면 전송 평면의
  append-only·dedup 규칙(0002 §1.4, §2.1)이 그대로 적용될 뿐이다.
- 제어 평면에 **잠금·리스·CAS·조건부 쓰기 조항이 없다.** `revoke`(§4.5)는 발급 자격을 끊는 것이지
  자원을 잠그는 것이 아니다.
- 기억 로그(append-only·결과적 일관성)와 상호배제(강한 일관성)는 요구가 반대다. 조정이 필요해지면
  그것은 이 로그 위도, 이 제어 평면 위도 아닌 다른 자리에 선다.

### 7.3 계정·멤버십·초대의 데이터 모델

**이 문서는 "토큰을 요청할 자격이 이미 있는 주체"를 전제로 시작한다.** 그 자격이 어디서 오는지 —
계정 생성, 워크스페이스 초대, 역할(owner/member), 베타 게이팅 — 는 제품 표면이고 별도 문서가
받는다.

이 문서가 그 경계에 남긴 이음매는 하나다: **§3.6의 grant 판정.** "판정이 발급 시점에 반드시
일어난다"와 "실패는 `403 not_grantable`"은 계약이고, **판정의 규칙**은 그 문서의 몫이다. 이음매를
계약으로 남겨 두었으므로, 데이터 모델이 정해질 때 이 문서를 고칠 필요가 없다.

## 8. 미결

이 문서가 **정하지 않은 것**과, 정하지 않은 이유.

1. **토큰의 서명 스킴과 검증 키 배포 형태.** §3.2가 만족해야 할 성질(자체 검증 가능, 전체 클레임
   서명, `keyId` 단위 무효화)까지 정했고 구체 스킴은 비워 뒀다. 이유: 대칭키(HMAC)냐 비대칭이냐,
   표준 포맷(JWS 계열)이냐 다른 형식이냐의 선택이 **라이브러리 의존과 키 관리 운영 절차를 함께
   끌고 오고**, 한번 발급을 시작하면 되돌리기 어렵다. mori-nest #4가 그런 갈림길을 스스로 정하지
   말고 `agent:decision`으로 올리라고 정했으므로 그렇게 한다. **스킴이 정해져도 §3.2~§3.5의
   조항은 바뀌지 않아야 한다** — 바뀌어야 한다면 그건 이 문서에 스킴 전제가 새어 들어간 것이다.
2. **런처 자격증명의 형태와 발급.** §1.1이 "작업공간 토큰과 구분 가능해야 한다"만 요구했다. 형태는
   §8-1과 함께 정하는 것이 자연스럽지만, 그 자격을 **누가 받을 수 있는가**는 계정·멤버십 모델
   (§7.3)이므로 이 문서가 답할 수 없다.
3. **grant 판정의 규칙.** 어떤 주체가 어떤 로그를 스코프에 실을 수 있는가. §3.6이 이음매를 계약으로
   남겼고 규칙은 §7.3의 문서 몫이다.
4. **로그의 폐기·삭제.** §2에 로그를 만드는 경로만 있고 없애는 경로가 없다. 0002 §1.4가 이벤트
   삭제를 금지했고 0002 §8-6이 보존(retention)을 미결로 남겼으므로, 로그 단위 삭제도 그 문제와 함께
   정해야 한다. 지금 정하면 전송 평면의 append-only와 부딪히는 조항을 제어 평면에 먼저 만들게 된다.
5. **작업공간 기록의 보존 기간.** §4.6의 조회가 언제까지 과거를 보여주는지 정하지 않았다. 유기
   기록을 너무 일찍 지우면 §4.7의 가시성이 그만큼 짧아지고, 영원히 두면 목록이 무한히 자란다.
   실제 작업공간 회전율을 보고 정하는 편이 낫다.
6. **한 작업공간이 실을 수 있는 로그 수의 상한.** §3.6은 하한(≥ 1)만 정했다. 상한은 0002 §8-5
   (로그 하나 = SSE 연결 하나)와 함께 봐야 한다 — 스코프에 로그를 많이 실을 수 있으면 클라이언트가
   그만큼 많은 구독을 열게 되고, 그때 HTTP/1.1 연결 수 제한에 걸린다.
7. **즉시·세밀한 폐기.** §3.5가 전송 평면 denylist를 채택하지 않았고, 그 결과 좁은 폐기의 수렴
   시간이 `tokenTtl`(≤ 15분)이다. 재검토 조건: 작업공간 수명이 시간 단위로 길어지거나, "즉시 +
   좁게"가 필요한 실제 사고가 한 번이라도 생기면 이 절을 다시 연다.
8. **시계 동기화 요구.** §3.3이 스큐 허용 상한(60초)만 정했다. 발급 서버와 전송 평면의 시계가 그
   이상 벌어졌을 때 어떻게 알아채는지(모니터링·자가 진단)는 배포 사항으로 남긴다. 조용히 벌어지면
   증상은 산발적 `401`로 나타나고 원인을 찾기 어렵다는 점만 적어 둔다.
9. **mori #115 본문과의 어긋남 1건 (0002 §8-10에서 이어짐).** #115는 커밋되는 정체성 파일에
   "hub 프로젝트 ID·**URL**"을 담는다고 적었는데, 0001 §2.5는 **프로젝트 ID만** 담고 hub 주소·
   자격증명은 절대 담지 않는다고 못박았다. **이 문서가 서버 쪽 답을 확정했다**: 제어 평면 베이스
   URL도 전송 평면과 마찬가지로 **런처 주입**이고(§1.1), 토큰은 런처가 받아 주입한다(§3.1).
   따라서 정체성 파일에 URL이 들어갈 자리는 서버 계약 어디에도 없다. **#115 본문과는 여전히
   어긋나며**, 클라이언트 쪽 변경은 이 문서의 범위가 아니므로 고치지 않고 `agent:decision`으로
   올린다 (mori-nest `CLAUDE.md` 하드 룰 4).
