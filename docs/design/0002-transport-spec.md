# 0002 — 전송 평면 와이어 스펙 (append / pull / subscribe)

상태: **초안.** 2026-08-04 작성. 2026-08-06 갱신 — §1.6(서버 파생 출처 값)이 추가됐다.
2026-08-07 갱신 — `mori-nest` #55(§Q5 S5): 되돌림(선별 제거)의 실행 형태가 **클라이언트가 읽는
무효 선언**으로 정해졌다. §1.4에 그 자리를 확인하는 문단이 붙고, §8-12가 닫혔으며, §8-6(보존)이
**모양까지** 닫혔다. §8-11(출처 노출)은 열려 있으나 미루기의 근거 하나가 만료됐다.
근거: [`0001-protocol-requirements.md`](./0001-protocol-requirements.md),
mori-nest [#1](https://github.com/shakystar/mori-nest/issues/1),
mori [#115](https://github.com/shakystar/mori/issues/115).

이 문서는 **전송 평면(dumb)만** 정한다. 0001 §1.4가 전송/제어 두 평면 경계를 계승할
불변식으로 세웠으므로 스펙도 그 경계로 나눈다. 토큰 **발급**·스코프 부여·작업공간 생애
추적(0001 §2.4, §2.5의 발급 쪽)은 후속 `0003` 제어 평면 스펙의 몫이다. 이 문서는 토큰을
**싣는 형식**까지만 정한다.

이 문서 안에서 **MUST / MUST NOT / MAY**는 계약이다. 그 외 서술은 근거다.

## 0. 이 문서가 정하는 것

전송 평면에는 경로가 셋뿐이다.

| 경로 | 메서드 | 라우트 | 하는 일 |
|---|---|---|---|
| append | `POST` | `/v1/logs/{logId}/events` | 이벤트를 민다 |
| pull | `GET` | `/v1/logs/{logId}/events` | 커서 이후를 당긴다 |
| subscribe | `GET` | `/v1/logs/{logId}/subscribe` | 새 이벤트를 밀어받는다 (SSE) |

이 셋 말고 전송 평면에 라우트를 추가하지 않는다. 위 세 라우트에 정의되지 않은 메서드는
`405`다 (§1.5).

---

## 1. 공통 계약

### 1.1 베이스 URL과 경로

베이스 URL은 **런처가 클라이언트에 주입한다.** 클라이언트는 그것을 다른 곳(리포에 커밋되는
정체성 파일 등)에서 유도하지 않는다 (0001 §2.5).

`{logId}`는 전송 평면이 아는 **유일한** 식별자다.

```
logId := ^[A-Za-z0-9_-]{1,128}$
```

- 서버는 `logId`를 **prefix-blind**하게 다룬다. `wsp_`/`psm_`/`proj_` 같은 접두사 의미를
  전송 평면이 해석하지 않는다 — 정규식 검증과 스코프 대조(§1.2)만 한다.
- 이 정규식은 경로 traversal 차단도 겸한다. 정규식에 맞지 않으면 `400 invalid_log_id`.
- **로그의 생성·발급은 이 문서 밖이다.** 전송 평면은 `logId`를 **주어진 것**으로 받는다.
  서버가 식별자를 mint하는 절차(0001 §1.4의 server-minted)는 `0003`이 정한다.

전신 서버가 쓰던 `/v1/projects/:id/events` 대신 `logs`를 쓰는 이유는 하나다: 전송 평면에
"프로젝트"라는 개념이 없기 때문이다. 그건 제어 평면의 어휘이고, 그 어휘가 라우트에
들어가면 전송 평면이 opaque하지 않다는 착시를 준다. 아직 구현이 없으므로 호환 부담도 없다.

### 1.2 인증과 스코프

```
Authorization: Bearer <token>
```

- 세 라우트 **모두** 이 헤더를 요구한다. 없거나 검증에 실패하면 `401 unauthenticated`.
- **토큰을 쿼리스트링·경로에 싣는 것을 금지한다** (MUST NOT). 쿼리스트링은 액세스 로그·
  프록시 로그·리퍼러에 그대로 남는다.
- 토큰은 **작업공간 단위로 발급**되고, 접근 가능한 `logId` 집합(스코프)을 담는다.
  요청 경로의 `logId`가 스코프 밖이면 `403 out_of_scope`.
- **스코프 판정은 fail-closed다** (MUST). 토큰에 스코프가 **없거나, 비어 있거나, 해석되지
  않으면 모든 요청을 거부한다** — "스코프가 없으니 전부 허용"으로 해석하는 것을 금지한다
  (MUST NOT). 스코프 필드가 빠졌을 때 조용히 전면 허용으로 무너지는 것이 이 종류 검사의
  전형적인 실패 방식이고, 그 결과는 cross-tenant 유출이다 (0001 §2.5).
- **스코프 강제는 서버의 의무다** (MUST). 클라이언트가 스코프를 스스로 정할 수 있으면
  그건 통제가 아니다 (0001 §2.5). 샌드박스 안의 에이전트는 런처가 준 토큰이 허용하는
  로그 밖으로 나갈 수 없다.
- 전송 평면은 **멤버십·계정 상태를 조회하지 않고** 토큰의 진위와 스코프를 판정할 수 있어야
  한다 (MUST). 즉 토큰은 자체 검증 가능한 형태로 스코프를 싣는다. 전송 평면이 계정 테이블을
  들여다보기 시작하면 두 평면 경계가 무너진다 (0001 §1.4). **어떤 형태로 그렇게 만드는지,
  수명·회전은 `0003`이 정한다.**
- 스코프 밖 로그에 대한 응답은 **그 로그의 존재 여부와 무관하게 동일해야 한다** (MUST) —
  같은 `403 out_of_scope`, 같은 본문. 없으면 404, 있으면 403으로 갈리면 그 자체가 로그 id
  열거 오라클이다.
- 토큰 값은 **응답 본문·에러 메시지·서버 로그 어디에도 실리지 않는다** (MUST NOT).

### 1.3 이벤트 봉투와 불투명성

와이어에 실리는 이벤트는 이것뿐이다.

```ts
type Event = {
  id: string      // ^[A-Za-z0-9_.:-]{1,256}$
  payload: unknown // 임의의 JSON 값. 서버는 해석하지 않는다
}
```

- 서버가 요구하는 필드는 `id` **하나뿐이다**. `payload`의 내부 구조에 대해 서버는 아무것도
  요구하지 않고, 아무것도 읽지 않는다 (MUST NOT). 타입·스키마·기억 taxonomy를 전송 평면이
  조금이라도 알면 클라이언트 스키마가 바뀔 때마다 서버를 함께 고쳐야 한다.
- 서버는 `payload` **안에 필드를 추가하지 않는다** (MUST NOT). 서버가 붙이는 것(커서)은
  봉투 바깥에만 붙는다.
- **바이트 보존**: 서버는 `payload`를 **받은 바이트 그대로** 저장하고 돌려준다 (MUST).
  객체 키 재정렬, 숫자 재표기(`1.0`→`1`), 유니코드 이스케이프 정규화, 공백 제거 — 어느 것도
  하지 않는다. 관찰 조건: append 요청 본문에서 잘라낸 `payload` 슬라이스와, 같은 이벤트를
  pull/subscribe로 받은 응답의 `payload` 슬라이스가 **바이트 동일**하다.
  이 조항이 있어야 클라이언트가 payload에 서명·MAC을 걸 수 있고, E2E 암호화를 나중에
  얹는 길이 막히지 않는다 (0001 §1.1). 암호 스킴 선택은 이 문서 밖이다.
- 요청·응답 본문은 UTF-8 JSON이다. `Content-Type: application/json`.
- **크기 한도**는 배포 파라미터다. 다만 계약상 하한을 둔다: 서버는 `maxEventBytes ≥ 1 MiB`,
  `maxRequestBytes ≥ maxEventBytes`를 만족해야 한다 (MUST). 초과하면 `413`이고, 그때
  응답의 `error.details`에 실제 한도를 실어야 한다 (MUST) — 클라이언트가 한도를 알아낼
  다른 경로가 없기 때문이다.

### 1.4 순서·커서·append-only

- 로그는 **append-only**다. 수용된 이벤트는 **수정되지도 삭제되지도 않는다** (MUST NOT).
  "retract"는 payload 안의 클라이언트 개념이지 전송 평면의 동작이 아니다.
- 서버는 이벤트를 수용하는 시점에 **로그 안의 전순서(total order)** 위 한 자리를 확정한다.
  한 번 확정된 상대 순서는 이후 어떤 요청·재부팅에도 바뀌지 않는다 (MUST).
  한 append 요청 안의 이벤트들은 **요청 배열 순서**를 그대로 보존한다 (MUST). 서로 다른
  요청 사이의 인터리브는 서버가 정한다.
- 그 자리를 가리키는 것이 **커서**다.

```ts
type Cursor = string  // 서버 발급 불투명 토큰
```

- 커서는 **서버가 발급한다.** 클라이언트는 커서를 **만들지도, 파싱하지도, 대소 비교하지도
  않는다** (MUST NOT). 클라이언트가 커서에 대해 할 수 있는 일은 "저장했다가 그대로 다시
  보내는 것"뿐이다.
- 커서는 로그 스코프다. 다른 로그의 커서를 보내면 미지 커서로 취급된다 (§3.2).
- 커서가 불투명하기 때문에 서버는 거기에 위치·오프셋·세그먼트를 직접 실을 수 있다.
  이건 허용이지 요구가 아니다 (§6.3).

#### 되돌림의 자리 — 위 첫 줄이 이미 정한 것

위 첫 줄의 *"retract는 payload 안의 클라이언트 개념"* 이 **되돌림(선별 제거)의 자리를
정하는 문장이다.** `selective-removal-and-retention-adjudication.md` §Q1이 후보 셋(읽기 경로
필터 / 클라이언트가 읽는 무효 선언 / 보존과 함께 실제 삭제)을 대조해 **무효 선언**을 골랐고,
그 자리가 바로 여기다. 새 조항이 아니라 이 줄의 확인이다:

- 되돌림은 로그에 **이벤트를 하나 더 미는 것**이다. 그 이벤트의 `payload`가 무엇을 무효로
  보는지를 담고, 서버는 그것이 무효 선언인지 알지 못한다 — §1.3이 payload 해석을 금지했다.
  전송 평면의 라우트(§0)·봉투(§1.3)·응답 스키마 어느 것도 이 때문에 늘지 않는다.
- **서버는 되돌림을 이행시키지 않는다.** 무효 선언을 읽고 자기 뷰에서 빼는 것은 소비자의
  몫이고, 무시하는 소비자를 서버가 막을 수단은 없다. 읽기 경로에서 서버가 대신 빼는 형태는
  §3.2의 조용한 누락 금지와 부딪히므로 고를 수 없다(같은 산정 §Q1.2). 서버가 지는 몫은
  *"되돌림 선언이 모든 소비자에게 같은 순서로 도달한다"* 까지다 — 그건 이 절과 §3·§4가
  이미 보장한다.
- 소비자가 *"이 무효 선언을 정당한 주체가 냈는가"* 를 가리려면 §1.6의 출처 값이 응답에
  실려야 하는데, 오늘은 실리지 않는다(§1.6 「노출」). §8-11이 그 자리다.

### 1.5 에러 형태와 상태코드

에러 응답은 어느 라우트든 같은 모양이다.

```ts
type ErrorResponse = {
  error: {
    code: string              // 기계가 분기하는 안정된 문자열
    message: string           // 사람이 읽는 설명
    details?: Record<string, unknown>
  }
}
```

- `code`는 안정된 계약이다. `message`는 바뀔 수 있으므로 클라이언트가 분기 근거로 삼지
  않는다.
- `message`·`details`에 **토큰·payload 원문을 싣지 않는다** (MUST NOT). 검증 실패를 설명할
  때도 실패한 필드 **이름**과 이벤트 `id`까지만 싣는다.

| 상태 | `code` | 언제 |
|---|---|---|
| `400` | `malformed_request` | 본문이 JSON이 아니거나 최상위 형태가 스키마와 다르다 |
| `400` | `invalid_log_id` | `{logId}`가 §1.1 정규식에 맞지 않는다 |
| `400` | `invalid_event` | 이벤트에 `id`가 없거나 정규식 위반, `payload` 키 부재 |
| `400` | `invalid_cursor_format` | `after`가 문자열이 아니다 (**미지 커서와 다르다** — §3.2) |
| `401` | `unauthenticated` | `Authorization` 부재·형식 오류·검증 실패 |
| `403` | `out_of_scope` | 경로의 `logId`가 토큰 스코프 밖 (존재 여부와 무관) |
| `405` | `method_not_allowed` | §0 표에 없는 메서드 |
| `406` | `not_acceptable` | subscribe에 `Accept: text/event-stream`이 없다 |
| `413` | `event_too_large` | 단일 이벤트가 `maxEventBytes` 초과. `details.maxEventBytes` 필수 |
| `413` | `request_too_large` | 요청 본문이 `maxRequestBytes` 초과. `details.maxRequestBytes` 필수 |
| `429` | `rate_limited` | 유량 제한. `Retry-After` 헤더 필수 |
| `500` | `internal` | 그 외 서버 결함 |
| `503` | `not_durable` | 내구화를 보장할 수 없다 (§2.2) |
| `503` | `unavailable` | 셧다운 중·의존 저장소 접근 불가. `Retry-After` 권장 |

### 1.6 서버 파생 출처 값 — 봉투 밖, 기록 안

**서버는 append를 수용할 때, 그 요청이 통과한 토큰의 클레임에서 파생한 출처 값을 이벤트
기록에 남긴다** (MUST). 이 값은 클라이언트가 보내는 것이 아니고, 와이어에도 나오지 않는다 —
서버가 자기 기록에만 남기는 값이다.

왜 필요한가: 0001 §2.4(작업공간 생애 추적)와 §2.5(런처가 주입하는 스코프 토큰)가 함께
성립하려면 *"이 이벤트를 어느 작업공간이 밀었는가"* 가 서버 안에서 답해질 수 있어야 한다.
그 답이 없으면 제어 평면이 아는 작업공간(`0003` §4)과 전송 평면이 든 이벤트 사이에 다리가
없고, 잘못 귀속된 기여를 특정할 방법도 없다. 다리는 append 시점에만 놓을 수 있다 — 로그는
append-only이므로(§1.4) **컬럼을 나중에 더해도 그 이전에 쌓인 이벤트의 출처는 영원히 비어
있다.**

#### 무엇을 적는가

| 값 | 어디서 오는가 | 무엇을 위한 것인가 |
|---|---|---|
| `workspaceId` | 검증된 토큰의 `workspaceId` 클레임 (`0003` §3.2) | **귀속·되돌림의 축.** 제어 평면의 작업공간 기록(`0003` §4.6)과 이 값으로만 이어진다 — 기간(`openedAt`/`endedAt`)·대상 로그(`logs`)·replica 축(`0003` §4.9)이 전부 그쪽에 있다 |
| `tokenId` | 검증된 토큰의 `tokenId` 클레임 (`0003` §3.2) | **발급 건의 축.** 한 작업공간이 갱신(`0003` §3.4)·멱등 재시도(`0003` §4.2)로 여러 토큰을 받으므로 `workspaceId`만으로는 어느 발급 건이 썼는지 갈리지 않는다. `0003` §3.8이 *"감사 기록이 토큰을 가리켜야 하면 `tokenId`를 쓴다"* 로 이미 이 축을 감사의 단위로 정해 뒀다 |

**둘 다 적는다** (MUST). 둘은 같은 질문에 답하지 않는다 — 귀속·되돌림은 작업공간 단위이고(그
기간과 스코프의 정본이 `0003` §4.6에 있다), 감사는 발급 건 단위다(`0003` §3.8). 하나로 줄이면
줄인 쪽의 질문이 답되지 않는다: `tokenId`만 적으면 되돌림이 매번 발급 기록을 한 번 더 거쳐야
하고, `workspaceId`만 적으면 `0003` §3.8이 정한 감사 단위가 이벤트 쪽에서 끊긴다.

**토큰 문자열 자체는 적지 않는다** (MUST NOT). 남기는 것은 위 두 클레임뿐이다 — `0003` §3.8이
서버 기록·감사 기록 어디에도 토큰 값을 남기지 못하게 했고, 이 조항은 그 규율의 예외가 아니다.
`scope`·`expiresAt` 같은 다른 클레임도 적지 않는다: 이 자리가 답해야 하는 질문은 *"누가
밀었는가"* 하나이고, 그 이상은 이벤트 행에 남을 이유가 없다.

#### 언제 적히는가 — 그리고 무엇도 그것을 덮지 못한다

- **출처 값은 그 이벤트를 처음 기록시킨 요청의 것이다** (MUST). §2.1의 dedup은
  first-write-wins이므로, 이미 있는 `id`를 다른 작업공간이 다시 밀어 `duplicate`로 분류되면
  **기존 행의 출처 값을 덮어쓰지 않는다** (MUST NOT). 덮어쓰기를 허용하면 나중에 미는 쪽이
  남의 이벤트 출처를 자기 것으로 바꿀 수 있고, 그 순간 이 축은 사칭 가능해진다 — 사칭 불가가
  이 축을 세운 이유이므로(아래) 그것을 잃으면 축 자체가 뜻을 잃는다.
- **출처 기록은 이벤트 기록과 같은 원자 단위 안에서 일어난다** (MUST). §2.1이 dedup 판정과
  기록을 원자적으로 요구했고, 출처 값이 그 원자 단위 밖에서 따로 쓰이면 *이벤트는 있는데
  출처는 비어 있는* 행이 크래시 창에서 표현 가능해진다. §2.2의 내구성 계약도 그대로 적용된다 —
  `200`이면 출처 값도 함께 내구화돼 있다.
- 따라서 이 값이 답하는 것은 **"그 바이트를 서버에 처음 남긴 것이 누구인가"** 이지 *"그 기억을
  만든 것이 누구인가"* 가 아니다. 유기된 작업공간의 미flush 기억을 다음 작업공간이 다시 미는
  경로(`0003` §4.1)에서는 실제로 민 쪽이 출처가 된다. 서버가 판정할 수 있는 것이 거기까지다
  (`0003` §4.8과 같은 층위).

#### 왜 사칭 불가인가

- **값의 유일한 출처는 그 요청이 통과한 토큰의 클레임이다** (MUST). 요청 본문·헤더·쿼리에서
  출처를 읽지 않는다 (MUST NOT). 요청이 §1.2의 인증을 통과하지 못하면 append 자체가 `401`이므로,
  출처 없이 기록될 수 있는 이벤트는 계약상 존재하지 않는다.
- **출처 값을 얻지 못한 채로 이벤트를 기록하지 않는다** (MUST NOT). 그런 상태에 이르면 `200`이
  아니라 `500 internal`이다 (MUST). 위 줄은 계약이 그런 이벤트를 허용하지 않는다는 말이지,
  구현이 저절로 그렇게 된다는 말이 아니다 — 검증 결과가 기록 층까지 **닿지 않은** 구현은 출처를
  비운 채 `200`을 돌려주고, 그것은 *검사할 것이 없으니 통과*의 전형이다. 이 경로가 조용한 이유는
  §1.4의 append-only 때문이다: 비운 채 수용한 이벤트의 출처는 **나중에 채울 수 없고**, 증상은
  기록 시점이 아니라 한참 뒤 되짚을 때 나타난다.
- 그 토큰은 **런처가 샌드박스 밖에서 발급받은 것**이다. `0003` §1.2 — *"제어 평면의 모든
  라우트는 런처 자격증명을 요구한다"* — 이고, `0003` §3.7이 작업공간 토큰으로 제어 평면에
  들어가는 경로와 토큰 교환 경로를 함께 막았다. **샌드박스 안의 에이전트는 자기 `workspaceId`를
  고를 수 없다.**
- 클레임은 서명에 덮여 있다(`0003` §3.2 성질 2). 클레임을 고쳐 쓰면 §1.2의 검증(`0003` §3.3
  검사 1)에서 `401`이다.
- 이것이 0001 §2.5 — *"신뢰 결정은 샌드박스 밖에 있어야 한다. 안에 있는 에이전트가 자기 권한을
  스스로 정할 수 있으면 그건 통제가 아니다"* — 를 이 축이 지키는 방식이다. 출처를 클라이언트가
  신고하는 형태였다면, 오귀속을 고치려고 만든 축을 오귀속시키는 쪽이 그대로 쓸 수 있다.

#### 왜 봉투 불변식(0001 §1.1, §5 표 1행)을 깨지 않는가

§1.3이 금지한 셋을 하나씩 대조한다.

1. **서버가 요구하는 필드가 늘지 않는다.** §1.3 *"서버가 요구하는 필드는 `id` 하나뿐이다"* —
   클라이언트는 여전히 `{id, payload}`만 보낸다. 출처를 신고할 자리가 요청 스키마에 생기지
   않으므로 봉투 정의(§1.3)와 append 요청(§2.1)이 글자 그대로 그대로다.
2. **`payload` 안에 필드가 추가되지 않는다.** §1.3 *"서버는 `payload` 안에 필드를 추가하지
   않는다"* — 이 값은 payload를 건드리지 않는다.
3. **바이트 보존이 그대로다.** §1.3의 바이트 보존 조항 — append 요청 본문에서 잘라낸 `payload`
   슬라이스와, 같은 이벤트를 pull/subscribe로 받은 응답의 `payload` 슬라이스가 여전히 **바이트
   동일**하다. 출처 값은 그 슬라이스 밖에 나란히 놓인다.

그리고 §1.3이 이 자리를 **이미 열어 뒀다** — *"서버가 붙이는 것(커서)은 봉투 바깥에만 붙는다."*
**출처 값은 커서와 같은 종류의 값이다**: 서버가 만들고, 봉투에 없고, 클라이언트가 제안할 수
없다. 다른 점은 하나뿐이고 그것이 아래다 — 커서는 응답에 실리고, 출처 값은 실리지 않는다.

#### 노출 — 기록만 하고 응답에 싣지 않는다

- **출처 값은 pull(§3.1)·subscribe(§4.3)의 응답에 실리지 않는다** (MUST NOT). `PullResponse`의
  `events[]` 항목은 `{id, payload, cursor}` 그대로이고, SSE 프레임 4종(§4.3)도 그대로다.
  **이 조항으로 바뀌는 와이어 계약은 0건이다** — 라우트 셋(§0)도, 에러 표(§1.5)도, 응답
  스키마도 늘지 않는다. 이 조항이 요구하는 변경은 **기록 층 하나**다.
- **왜 노출을 함께 열지 않는가.** 나중에 응답에 싣는 것은 필드 하나를 더하는 것이고, 이미 나간
  필드를 거두는 것은 클라이언트를 깨는 것이다. 비용이 한쪽으로 크게 기운 선택이므로 싼 쪽에서
  시작한다. 이 축의 첫 소비자는 서버 자신이므로 노출이 없어도 막히는 것이 없다.
- **넓히는 경로**는 열어 둔다: 실어야 할 이유가 생기면 `events[]`와 SSE `append` 프레임에 필드를
  더하는 형태이고(커서가 이미 그 자리에 있으므로 새로운 종류의 값은 아니다), 그때 함께 답해야
  하는 것은 *"출처를 볼 자격이 누구에게 있는가"* 다 — §8 미결.

## 2. append — 이벤트를 민다

### 2.1 요청과 응답

```
POST /v1/logs/{logId}/events
Authorization: Bearer <token>
Content-Type: application/json
```

```ts
type AppendRequest = {
  events: Event[]   // 길이 ≥ 1
}
```

```ts
type AppendResponse = {
  accepted:  { id: string; cursor: Cursor }[]  // 이번 요청으로 새로 기록됨
  duplicate: { id: string; cursor: Cursor }[]  // 이미 있던 id — 무시됨
}
```

성공 상태코드: **`200 OK`**. (`201`도 `202`도 쓰지 않는다 — `202 Accepted`는 "받았지만
아직 안전하지 않다"를 뜻하는 코드이고, 이 스펙에는 그 상태가 존재하지 않는다. §2.2)

- `accepted`는 **요청 배열 순서**를 보존한다. `duplicate`의 `cursor`는 **먼저 저장돼 있던
  사본**의 커서다 (이번 요청이 위치를 바꾸지 않는다).
- **id 기준 멱등 dedup**: 같은 `id`가 이미 있으면 새 것을 기록하지 않고 `duplicate`로
  분류한다. **first-write-wins**이며, 이건 에러가 아니다 (0001 §1.2).
  서버는 payload 바이트를 **비교하지 않아도 된다** — 같은 id로 다른 바이트를 밀면 먼저 것이
  남고 나중 것은 조용히 버려진다. 이 침묵을 깰지는 §8 미결.
- **동시 append에 대해 dedup 판정과 기록은 원자적이다** (MUST). 같은 `id`를 담은 요청 두
  건이 동시에 도착해도 로그에 그 이벤트는 **정확히 한 번** 나타나고, 정확히 한 요청만
  `accepted`로, 나머지는 `duplicate`로 응답한다. "있는지 보고 없으면 쓴다"를 원자적이지 않게
  구현하면 두 요청이 모두 빈 로그를 보고 둘 다 쓴다 — 그 순간 §1.2의 멱등 dedup이 깨지고,
  §2.4의 재시도 안전성도 함께 깨진다.
- **`events`가 빈 배열이면 `400 malformed_request`다** (MUST). 빈 요청을 `200`으로 돌려주면
  클라이언트의 flush 경로가 "밀었다"고 오인한다 — 아무것도 검사하지 않은 것이 통과로 보이는
  형태를 계약에 남기지 않는다.
- **검증은 all-or-nothing이다**: 요청 안 이벤트 중 하나라도 §1.3 검증에 실패하면 `400`이고
  **아무것도 기록하지 않는다** (MUST). `details.eventId`에 첫 번째 실패 이벤트의 id를 싣는다.
  요청 안에 같은 `id`가 두 번 이상 있으면 `400 invalid_event`다 (MUST) — 한 요청 안에서
  first-write-wins를 적용하면 클라이언트가 무엇이 버려졌는지 모른 채 성공을 받는다.
- append 응답에는 **로그의 head 커서가 없다.** 의도적이다. 다른 writer가 동시에 밀고 있을 수
  있으므로, append 응답의 커서로 "여기까지 다 받았다"를 유도하면 그 사이 이벤트를 건너뛴다.
  "어디까지 봤는가"는 pull/subscribe에서만 얻는다.

### 2.2 `accepted` = 내구화 완료

**응답이 `200`이면, `accepted`와 `duplicate`에 실린 모든 id는 이미 내구화돼 있다.**
"받았다"와 "디스크에 안전하다"를 구분하는 상태는 **와이어에 존재하지 않는다** — 그것이 이
조항의 요점이다. 서버가 내구성을 보장할 수 없으면 `200`이 아니라 `503 not_durable`이다
(MUST).

이게 왜 이렇게까지 중요한가: mori는 db를 임시 작업공간 안에 두고, 그 작업공간은 작업이
끝나면 지워진다. **push 성공이 "이 작업공간을 죽여도 된다"의 유일한 근거다** (0001 §2.2).

#### 관찰 가능한 조건

내구성을 **계약**으로 적는다. fsync를 부르는지, WAL을 쓰는지, 복제본 몇 개에 쓰는지는
구현 선택이고 이 문서가 정하지 않는다. 이 문서가 정하는 것은 그 구현이 **만족시켜야 하는
관찰 가능한 성질**이다.

> `200` 응답의 마지막 바이트를 클라이언트가 받은 시점 이후 언제든, 서버 프로세스를
> `kill -9` 하고 호스트를 전원 차단한 뒤 서버를 다시 띄운다. 그다음 같은 로그를
> `after` 없이 pull하면, 그 응답의 `accepted` ∪ `duplicate`에 있던 **모든 id가 그대로,
> 같은 상대 순서로** 나타난다.

- "언제든"이 중요하다. 응답 직후 몇 밀리초 안에 죽여도 성립해야 한다. 뒤늦게 flush하는
  구현은 이 시험을 통과하지 못한다.
- 전원 차단까지 포함한 이유: OS 페이지 캐시까지만 쓰고 응답하는 구현은 프로세스 kill은
  견디지만 전원 차단은 못 견딘다. 그리고 그 구멍이 정확히 0001 §3.1이 지목한 것이다.
- 이 시험은 **수용 응답에 대해서만** 성립한다. 그 역은 성립하지 않는다 — 아래.

#### 역은 보장되지 않는다

**`accepted`에 없다고 해서 기록되지 않았다는 뜻이 아니다.** 서버가 기록을 마치고 응답을
쓰다가 죽으면, 클라이언트는 실패를 보지만 이벤트는 남아 있다. 비-2xx 응답은 **아무것도
약속하지 않는다.**

이 비대칭이 문제가 되지 않는 이유는 dedup 때문이다 — §2.4.

### 2.3 단건 write-through가 계약상 1급 경로

- **서버는 `events` 길이 1을 정상 경로로 받아들인다** (MUST). 배치는 이 계약의 전제가
  아니다. 최소 배치 크기, 최소 요청 간격, 배치 전용 엔드포인트 — 어느 것도 없다 (MUST NOT).
- 기억이 생길 때마다 미는 것이 **기본값**이다. 여럿이 쓰는 하네스에서 "동료가 내 결정을
  언제 보는가"가 곧 협업의 품질이고, 세션 경계 배치 push는 그 조건을 만족하지 못한다
  (0001 §0, §2.3).
- **배치와 debounce는 클라이언트 측 최적화다.** 쓰기 증폭이 문제가 되면 클라이언트가 짧은
  debounce(1초 수준)로 묶을 수 있다. 그건 클라이언트의 선택이며, 서버는 그것을 요구하지도
  가정하지도 않는다.
- 유량 제한을 두는 배포가 있다면 그건 `429`(§1.5)로 표현한다. **"배치로 묶어라"는 요구를
  계약에 넣는 방식으로 표현하지 않는다** (MUST NOT).

### 2.4 재시도

- 타임아웃·`5xx`·연결 끊김을 만난 클라이언트는 **같은 요청을 그대로 다시 보낸다.** 같은
  `id`를 다시 밀면 `duplicate`로 분류되므로(§2.1) 재시도는 언제나 안전하고, 이벤트가 두 번
  기록되지 않는다.
- 이것이 0001 §1.2("id 기준 멱등 dedup … write-through 재시도를 공짜로 만드는 근거")가
  전송 평면에서 실제로 쓰이는 자리다. 이게 없으면 §2.2의 비대칭(역이 보장되지 않음)이
  중복 기록으로 바로 이어진다.
- 재시도가 `200`을 받으면 §2.2가 그대로 적용된다 — `duplicate`로 분류된 것도 내구화돼 있다.

## 3. pull — 커서 이후를 당긴다

### 3.1 요청과 응답

```
GET /v1/logs/{logId}/events?after=<cursor>&limit=<n>
Authorization: Bearer <token>
```

| 쿼리 | 필수 | 의미 |
|---|---|---|
| `after` | 아니오 | 이 커서 **다음**부터. 없으면 로그의 처음부터 |
| `limit` | 아니오 | 이 응답에 실을 최대 이벤트 수. 서버가 더 작게 깎을 수 있다 |

```ts
type PullResponse = {
  events: { id: string; payload: unknown; cursor: Cursor }[]
  cursor?: Cursor        // events의 마지막 이벤트 커서. events가 비면 없음
  hasMore: boolean       // cursor 뒤에 더 있는가
  from: "beginning" | "known" | "unknown"
}
```

성공 상태코드: **`200 OK`**. 빈 로그도 `200`이다 (`{ events: [], hasMore: false,
from: "beginning" }`).

- `events`는 §1.4의 전순서대로 실린다 (MUST).
- 다음 페이지는 `after=<응답의 cursor>`로 다시 요청한다. `hasMore`가 `false`가 될 때까지
  반복한다. `hasMore: true`면 `events`는 비어 있지 않다 (MUST).
- `limit`은 서버가 상한을 둘 수 있다. 클라이언트가 더 작게 요청하면 그대로 따른다.
  **`limit`은 페이지 크기일 뿐 필터가 아니다** — 잘려나간 이벤트는 사라지지 않고 다음
  페이지에 그대로 있다.
- **`limit`은 커서 해석과 정렬이 끝난 뒤에 적용한다** (MUST). 시작점(`after` 다음, 또는
  로그의 처음)에서 **앞에서부터** `limit`건을 취하고, `hasMore`는 그 뒤에 남은 것이 있는지로
  정한다. 뒤에서 자르거나(최신 N건만 남기기) 커서 해석 전에 자르면, `from: "unknown"`으로
  처음부터 읽는 경우에 **가장 오래된 구간이 통째로 사라진다** — §3.2의 전량 반환이 그
  자리에서 무의미해진다.
- `from`은 서버가 **어디서부터 읽기 시작했는지**를 알려준다. 클라이언트는 이 값으로 자기
  커서가 무효화됐음을 안다.

### 3.2 미지 커서 → 전량 반환

**`after`가 이 로그에서 해석되지 않으면, 서버는 로그의 처음부터 반환한다** (MUST) —
`from: "unknown"`.

- 미지 커서에 대해 **현재 head부터 주는 것을 금지한다** (MUST NOT). 그건 조용한 누락이고,
  클라이언트는 자기가 무엇을 못 받았는지조차 알 수 없다.
- 미지 커서를 **에러로 만들지 않는다** (MUST NOT). `400 invalid_cursor_format`은 `after`가
  문자열조차 아닐 때만이고, "형식은 맞는데 이 로그에서 해석 안 됨"은 정상 응답이다.
- 덜 주는 것보다 더 주는 것이 안전하다. **클라이언트가 `id`로 dedup한다** (0001 §1.3, §1.2).
- "전량 반환"은 **시작점이 로그의 처음이라는 뜻이지, 한 응답에 다 싣는다는 뜻이 아니다.**
  큰 로그는 `limit`/`hasMore`로 페이지가 나뉜다. 전량은 페이지를 이어 받아 완성된다.
- 미지 커서가 생기는 경로: 다른 로그의 커서, 저장소가 재구축돼 커서 표현이 바뀐 경우,
  클라이언트가 커서를 손상시킨 경우. 어느 쪽이든 서버의 대응은 하나다.

**이 문서 전체를 관통하는 규칙**: 서버는 **과잉 전달**하거나 **명시적으로 갭을 알린다.**
조용한 누락은 어느 경로에서도 허용되지 않는다 (MUST NOT). subscribe에서 이 규칙이 어떻게
적용되는지는 §4.5.

## 4. subscribe — 새 이벤트를 밀어받는다

### 4.1 전송 방식: **SSE** (Server-Sent Events)

WebSocket·롱폴링·gRPC 스트리밍이 아니라 SSE를 고른다. 근거:

1. **방향이 요구와 맞는다.** 필요한 것은 서버→클라이언트 단방향 푸시뿐이다. 밀기는 별개의
   `POST`이고 단건 write-through가 1급 경로이므로(§2.3), 양방향 채널이 필요한 자리가 없다.
   WebSocket을 고르면 그 소켓 위로 요청/응답을 태우고 싶어지고, 그 순간 전송 평면에 세션
   상태와 제어 의미가 스며든다 — 0001 §1.4의 두 평면 경계가 거기서 무너진다.
2. **재개 메커니즘이 프로토콜에 이미 있다.** SSE의 `id:` 필드와 `Last-Event-ID` 재접속
   헤더가 커서 재개와 정확히 같은 모양이다. 우리가 커서를 실어 나를 자리를 새로 만들 필요가
   없고, **pull 폴백과 같은 커서**를 쓴다(§4.5).
3. **평범한 HTTP/1.1 응답이다.** 리버스 프록시·게이트웨이가 `Upgrade` 핸드셰이크 없이
   통과시킨다. 전송 평면을 런타임 의존 없이(`node:http` 수준) 구현할 수 있다. WebSocket은
   프레이밍·핑퐁·서브프로토콜 협상을 이 스펙에 추가로 정의하게 만든다 — 전송 평면을 dumb하게
   유지하려는 목적과 반대 방향이다.
4. **데몬 중립이다.** 로컬 데몬이든 원격 hub든 같은 HTTP 응답이다 (§7.1).

받아들이는 비용:

- **브라우저의 `EventSource`는 쓸 수 없다.** 헤더를 실을 수 없는데 §1.2가 쿼리스트링 토큰을
  금지하기 때문이다. 브라우저 클라이언트가 필요해지면 `fetch` 스트림 리더로 SSE를 파싱한다
  (헤더를 실을 수 있다). mori 클라이언트는 브라우저가 아니므로 지금 문제되지 않는다.
- HTTP/1.1에서 연결 하나가 로그 하나에 묶인다. 다중 로그 구독은 §8 미결.

### 4.2 요청

```
GET /v1/logs/{logId}/subscribe?after=<cursor>
Authorization: Bearer <token>
Accept: text/event-stream
```

`Accept: text/event-stream`이 없으면 `406 not_acceptable`.

시작 위치는 `after` 쿼리, 없으면 `Last-Event-ID` 헤더에서 읽는다. **둘 다 있으면 `after`가
이긴다** (클라이언트가 명시한 쪽). 둘 다 없으면 로그의 처음부터다 — pull과 같은 규칙이다
(§3.2). "지금부터"를 뜻하는 값은 이 스펙에 **없다**.

성공 상태코드: **`200 OK`**.

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-store
Connection: keep-alive
```

에러(`401`/`403`/`400`/`429`/`503`)는 스트림을 열기 전에 §1.5의 JSON 본문으로 응답한다.
스트림이 열린 뒤에 발생한 문제는 `event: reset`으로 알린다(§4.5) — 이미 `200`을 보냈으므로
상태코드를 바꿀 수 없다.

배포 주의: 중간 프록시가 응답을 버퍼링하면 SSE가 죽는다. 프록시 버퍼링을 꺼야 한다
(예: nginx `X-Accel-Buffering: no`). 이건 배포 사항이지 계약이 아니다.

### 4.3 프레임

| `event:` | `data:` | 언제 |
|---|---|---|
| `open` | `{ "from": "beginning" \| "known" \| "unknown" }` | 연결 직후 1회, 항상 첫 프레임 |
| `append` | `{ "id": string, "payload": unknown, "cursor": Cursor }` | 이벤트 하나당 하나 |
| `heartbeat` | `{}` | 유휴 시 주기적 |
| `reset` | `{ "reason": string }` | 스트림으로 이어갈 수 없다 → pull로 내려가라 |

- `append` 프레임에는 SSE `id:` 줄에 그 이벤트의 커서를 싣는다 (MUST). 재접속 시
  `Last-Event-ID`로 되돌아오는 값이 이것이다.
- **이벤트 하나당 프레임 하나다** (MUST). 단건 write-through가 1급 경로이므로 스트림도
  묶음을 전제하지 않는다.
- `from`의 의미는 pull의 `from`과 같다(§3.1). `unknown`이면 서버가 로그 처음부터 재생한다.
- **`heartbeat`는 유휴 15초 이내마다 보낸다** (MUST). 클라이언트는 이것으로 죽은 연결을
  감지한다 — TCP만 믿으면 끊긴 연결을 몇 분씩 살아 있다고 오인한다. 클라이언트는 하트비트를
  연속 2회 놓치면 끊긴 것으로 보고 §4.5로 간다.
- 알 수 없는 `event:` 이름은 클라이언트가 **무시한다** (MUST) — 나중에 프레임 종류를 늘릴
  여지를 남긴다.

### 4.4 전달 보장

- **이벤트는 내구화된 뒤에만 스트림에 실린다** (MUST). 구독자가 §2.2를 통과하지 않은
  이벤트를 먼저 보는 일은 없다. 안 그러면 구독자가 "있다"고 본 것이 재부팅 후 사라진다.
- 스트림은 **at-least-once**다. 재접속·재생으로 같은 이벤트가 다시 올 수 있다. 클라이언트가
  `id`로 dedup한다 (0001 §1.2).
- 스트림 안에서 이벤트는 §1.4의 전순서대로 온다 (MUST).
- **스트림은 내구성 경로가 아니다.** "구독으로 받았다"는 아무것도 대체하지 않으며, 특히
  push 성공(§2.2)을 대체하지 않는다.

### 4.5 끊김·백프레셔 → pull 폴백

구독이 끊긴 구간의 복구 경로는 **커서 기반 pull이다** (0001 §2.1). 스펙이 요구하는 절차:

1. 클라이언트는 마지막으로 받은 `append` 프레임의 커서를 보관한다.
2. 연결이 끊기면(전송 오류, 하트비트 2회 누락, `reset` 수신) 그 커서로
   `GET /v1/logs/{logId}/events?after=<cursor>`를 `hasMore: false`가 될 때까지 돌린다.
3. 그 pull의 마지막 커서로 `subscribe?after=<cursor>`를 다시 연다.
4. 커서를 하나도 못 받은 상태로 끊겼으면 `after` 없이 2번을 한다 — 전량을 받고 dedup한다.

서버 쪽 의무:

- **재생할 수 없으면 조용히 건너뛰지 말고 `event: reset`을 보내고 스트림을 닫는다** (MUST).
  요청된 커서에서 이어줄 수 없을 때, 서버가 택할 수 있는 것은 **로그 처음부터 재생**(과잉
  전달)이거나 **`reset`**(명시적 갭 통보)이지, "현재 head부터 조용히 시작"이 아니다
  (MUST NOT). §3.2의 규칙이 여기서도 그대로다.
- **느린 구독자를 무한히 버퍼링하지 않는다** (MUST NOT). 밀린 양이 서버의 한도를 넘으면
  `event: reset`을 보내고 닫는다. 클라이언트는 pull로 따라잡고 다시 연결한다. 이 조항이
  없으면 느린 구독자 하나가 서버 메모리를 끌고 간다 (0001 §3.2와 같은 함정).
  **밀린 이벤트를 버리고 스트림을 이어가는 것은 금지한다** (MUST NOT) — 버퍼 상한을 넘겼을
  때 오래된 쪽을 떨어뜨리고 계속 보내면, 클라이언트는 연속된 스트림을 받았다고 믿으면서
  가운데가 비어 있다. 한도를 넘겼으면 반드시 닫고 `reset`으로 알린다.
- `reset`의 `reason`은 사람이 읽는 설명이다. 클라이언트의 대응은 이유와 무관하게 하나다:
  pull로 따라잡고 다시 연다.

## 5. 계승 불변식 대조표 (0001 §1)

0001 §1의 네 불변식이 이 스펙의 **어느 조항으로** 표현됐는지 1:1로 짚는다.

| # | 불변식 (0001 §1) | 표현됐는가 | 스펙 조항 |
|---|---|---|---|
| 1 | **불투명 페이로드** — 서버는 이벤트 내용을 해석하지 않고 `id` 외에는 요구하지 않는다 | 예 | §1.3 봉투가 `id`+`payload`뿐, 서버의 payload 해석·필드 추가 금지, 바이트 보존 규칙 / §1.2 인가는 `logId` 스코프만 보고 payload를 참조하지 않는다 / §1.1 전송 평면은 prefix-blind / §1.5 에러 본문에 payload 원문 금지 |
| 2 | **id 기준 멱등 dedup** — 같은 id를 다시 밀면 무시된다 | 예 | §2.1 `duplicate` 분류 + first-write-wins(에러 아님) + **동시 append에서의 원자성** / §2.4 재시도가 항상 안전하다는 것을 이 위에 세운다 / §4.4 스트림 at-least-once의 안전 근거 / §3.2 전량 반환이 안전한 근거 |
| 3 | **append-only + 순서 보존, 미지 커서 → 전량 반환** | 예 | §1.4 수정·삭제 금지, 전순서 확정 후 불변, 요청 배열 순서 보존 / §3.1 pull이 전순서대로 반환 + `limit`은 커서 해석·정렬 **이후** 적용 / §4.4 스트림도 같은 순서 / §3.2 미지 커서 전량 반환 + 조용한 누락 금지 / §4.5 스트림에서의 같은 규칙(밀린 이벤트 폐기 금지) |
| 4 | **두 평면 경계** — 전송(dumb)/제어(smart) 분리, 식별자는 서버 발급 | **부분** | 표현된 쪽: §1.1 경로가 `logId`만 알고 prefix 의미를 해석하지 않음 / §1.2 전송 평면이 멤버십·계정을 조회하지 않고 토큰 자체 검증 / §7.2 잠금·CAS 조항 없음 / §0 라우트 셋 고정. **표현되지 않은 쪽**: **식별자 발급(server-minted) 자체가 이 문서에 없다** |

**§1.6(서버 파생 출처 값)은 1행을 바꾸지 않는다.** 그 조항이 1행의 근거 셋 — 봉투가
`id`+`payload`뿐 / payload 해석·필드 추가 금지 / 바이트 보존 — 어느 것도 건드리지 않는다는
대조가 §1.6 안에 있다. 값이 봉투 **밖**(§1.3이 커서에게 열어 둔 자리)에 서기 때문이다.
4행(두 평면 경계)에 대해서도 같다: 출처 값은 제어 평면의 어휘를 전송 평면이 **해석**하는 것이
아니라, 자기가 이미 검증한 토큰의 클레임을 그대로 옮겨 적는 것이다 — 전송 평면은 그 문자열의
뜻을 묻지 않고, 뜻을 아는 쪽은 `0003` §4가 든다.

#### 4번이 부분인 이유

식별자 발급은 정의상 **제어 평면의 행위**다 — "누구에게 어떤 로그를 주는가"는 판단이고,
그 판단을 dumb transport에 넣는 순간 전송 평면이 opaque하지 않게 된다. 그래서 이 문서는
`logId`를 **주어진 것**으로 받는 자리(§1.1)와, 그 발급이 `0003`의 몫이라는 사실만 적는다.
전송 평면이 지는 몫(prefix-blind, 계정 미조회, 스코프 강제)은 위 표대로 모두 표현돼 있다.
**빠진 것은 이 문서가 다룰 수 없는 것이지, 누락이 아니다.**

## 6. 0001 §3의 구현 갭 4건 — 스펙이 막는가

0001 §3은 넷 다 **구현** 결함이며 와이어에 보이지 않는다고 적었다. 그러니 스펙이 막을 수
있는 것과 없는 것이 갈린다. **막는다고 적은 것은 그 조항이 실제로 이 문서에 있다.**

| 갭 (0001 §3) | 스펙이 막는가 | 근거 |
|---|---|---|
| **3.1 fsync 없음** | **막는다** | §2.2가 `200` ⇒ 내구화를 계약으로 못박고, `kill -9` + 전원 차단 후 pull에 남아 있어야 한다는 **관찰 가능한 조건**으로 적었다. 보장 못 하면 `503 not_durable`(§1.5)이지 `200`이 아니다. 어떻게 만족시킬지(fsync·WAL·복제)는 구현 선택이지만, 페이지 캐시까지만 쓰고 응답하는 구현은 이 조항을 **위반**한다 |
| **3.2 전량 인메모리** | **막지 않는다 — 구현 제약으로 넘긴다** | 상주 메모리는 와이어에서 관찰되지 않는다. 다만 스펙이 그것을 **강요하지 않도록** 두 곳을 열어 뒀다: §3.1의 `limit`/`hasMore`가 "응답 하나에 로그 전체"를 요구하지 않고, §4.5가 느린 구독자의 무한 버퍼링을 **금지**한다. 즉 스펙은 인메모리를 요구하지 않고, 오히려 무한 버퍼링 쪽은 명시적으로 막는다 |
| **3.3 pull이 O(n)** | **막지 않는다 — 구현 제약으로 넘긴다** | 복잡도는 계약이 아니다. 다만 §1.4가 커서를 **서버 발급 불투명 토큰**으로 정의하고 클라이언트의 생성·해석·비교를 금지했으므로, 서버는 커서에 위치·오프셋·세그먼트를 직접 실어 O(1)로 해석할 자유가 있다. 구 구현이 `findIndex`로 훑은 것은 커서가 "이벤트 id"였기 때문인데, 이 스펙에는 그 강제가 없다. **스펙은 길을 열어 둘 뿐 O(1)을 요구하지 않는다** |
| **3.4 부팅 시간 선형** | **막지 않는다 — 구현 제약으로 넘긴다** | 이 문서 어디에도 "부팅 시 전 이벤트를 재생하라"는 조항이 없다. §1.4의 순서 불변과 §2.2의 내구성만 만족하면 스냅샷·파생 인덱스 압축은 자유다. **단, §1.4의 append-only가 수용된 이벤트의 삭제를 금지하므로**, "오래된 이벤트를 버려 부팅을 줄이는" 형태의 compaction은 **스펙이 막는다** — 허용되는 것은 파생 인덱스·스냅샷의 압축뿐이다 |

## 7. 이 문서가 전제하지 않는 것

### 7.1 로컬 데몬의 유무 (0001 §4.1 미결)

**이 스펙은 데몬이 있든 없든 동일하다.** 0001 §4.1이 *"양쪽이 같은 프로토콜이면 클라이언트
입장에서 동작은 동일하다"*고 적었으므로, 데몬 존재를 전제한 조항을 이 문서에 넣지 않는다.

구체적으로 지킨 것:

- 베이스 URL은 런처가 주입한다(§1.1). `localhost`·유닉스 소켓·특정 포트를 스펙이 정하지
  않는다. 같은 클라이언트가 로컬 데몬을 가리키든 원격 hub를 가리키든 코드가 같다.
- 인증 형식(§1.2)이 양쪽에 같다. 로컬이라고 토큰을 생략하는 예외를 두지 않았다.
- SSE를 고른 이유 4번(§4.1)이 이것이다 — 평범한 HTTP 응답이라 양쪽에서 같은 모양이다.

**데몬을 둘 것인가는 이 문서가 결정하지 않는다.** 결정되더라도 이 문서는 바뀌지 않아야
한다. 바뀌어야 한다면 그건 이 문서에 데몬 전제가 새어 들어갔다는 신호다.

### 7.2 조정(mutual exclusion)은 여기 없다

**전송 평면에 잠금·리스·CAS·조건부 쓰기 조항이 없다** (0001 §4.2). 의도적이다.

- append는 조건부가 아니다. `If-Match`류 헤더도, "커서가 X일 때만 써라"도 없다.
- dedup(§2.1)은 **멱등성**이지 상호배제가 아니다. 같은 id의 두 번째 쓰기를 버리는 것이지,
  두 writer 중 하나를 이기게 하는 것이 아니다.
- 기억 로그(append-only·결과적 일관성)와 상호배제(강한 일관성)는 요구가 반대이므로 **같은
  자리에 두지 않는다** — 0001 §4.2가 정해 둔 데까지다. 조정이 필요해지면 그것은 이 로그
  위가 아니라 다른 자리에 선다.

## 8. 미결

이 문서가 **정하지 않은 것**과, 정하지 않은 이유. **닫힌 항목도 지우지 않는다** — 이 목록은
미결 목록이면서 동시에 결정 이력이다. 항목 머리의 `[닫힘 …]`이 그 자리가 무엇으로 닫혔는지를
말한다 (`0003 §8`과 같은 관례).

1. **로그·토큰의 발급.** `logId`를 누가 언제 mint하는지, 토큰의 수명·회전·폐기, 작업공간
   생애 추적(0001 §2.4)은 전부 `0003` 제어 평면 스펙의 몫이다. 이 문서는 토큰을 **싣는
   형식**(§1.2)까지만 정했다.
2. **토큰의 구체적 형태.** §1.2는 "전송 평면이 멤버십 조회 없이 스코프를 검증할 수 있어야
   한다"는 **성질**만 요구한다. 서명된 자체 기술 토큰인지, 다른 방식인지는 `0003`.
3. **같은 id·다른 바이트.** §2.1은 first-write-wins에서 멈춘다. payload는 불투명하지만
   바이트 비교는 해석 없이도 가능하므로, 서버가 불일치를 감지해 응답에 표시하는 선택지가
   있다. 지금 정하지 않는 이유: 그러려면 서버가 기존 바이트를 읽어와야 해서 append 경로가
   비싸지는데, 그 비용을 감수할 만한 실제 오용 사례를 아직 못 봤다. 정한다면 `duplicate`
   항목에 플래그를 더하는 형태가 될 것이다.
4. **payload를 임의 JSON으로 둘 것인가, base64 문자열로 조일 것인가.** §1.3의 바이트 보존을
   base64 문자열로 조이면 구현이 훨씬 쉬워진다(원문 슬라이스를 붙잡을 필요가 없다). 대신
   payload가 사람에게 안 읽히고 크기가 4/3배가 된다. E2E 스킴(0001 §1.1, 비범위)이 정해지면
   함께 재검토한다.
5. **로그 하나 = 연결 하나.** 여러 로그를 한 SSE 연결로 구독하는 형태는 정하지 않았다.
   클라이언트가 여러 로그를 동시에 보게 되면(워크스페이스 다중 바인딩) HTTP/1.1 연결 수
   제한에 걸린다. 지금 정하지 않는 이유: 로그를 몇 개나 동시에 보게 되는지가 제어 평면
   모델(`0003`)에 달려 있다.
6. **[닫힘 2026-08-07 — 모양까지] 보존(retention).** §1.4는 삭제를 금지했으므로 로그는 무한히
   자란다. 오래된 이벤트를 어떻게 할 것인가(콜드 스토리지 이동, 스냅샷 후 절단)는 전송 평면
   만으로 답할 수 없다 — 절단은 §3.2의 "전량 반환"과 정면으로 부딪히므로 클라이언트 부트스트랩
   모델과 함께 정해야 한다. **받은 자리**:
   `selective-removal-and-retention-adjudication.md` §Q2 — 그 산정이 §8-12·`0003 §8-4`와
   합동으로 이 축을 받았다. 닫힌 것은 **어떤 모양의 답이 허용되는가**까지다:
   - **허용 — 오늘 계약 그대로.** 콜드 스토리지 이동, 파생 인덱스·스냅샷 압축(§6 표 3.4행이
     이미 허용). 전량 반환이 여전히 전량이므로 §3.2와 부딪히지 않는다. 자라는 것은 바이트지
     응답 크기가 아니다(§3.1의 `limit`/`hasMore`).
   - **금지 — 조용한 절단.** 절단해 놓고 `from: "unknown"`으로 "처음부터 줬다"고 응답하는 것.
     절단된 로그의 "처음"은 서버가 임의로 옮긴 head이고, 그건 §3.2가 막은 그것이다. 새 replica가
     미지 커서로 붙었을 때 무엇을 못 받는지는 산정 §Q2.3의 인터리브에 있다.
   - **열려 있는 것 — 절단을 열려면 함께 답해야 하는 것 둘.** ① §3.2의 관통 규칙은 *"과잉
     전달하거나 명시적으로 갭을 알린다"* 이므로 절단 자체가 위반인 것이 아니라 **조용함**이
     위반이다 — 갭을 알릴 자리(`from`에 값을 더하는 형태)가 필요하고 그건 와이어 계약 변경이다.
     ② 절단점 이전 `id`를 다시 밀면 §2.1의 first-write-wins가 `accepted`를 주어 그 이벤트가
     **새 커서로 되살아난다** — §1.4의 전순서 불변이 거기서 깨지므로 dedup 규율을 함께 고쳐야
     한다.
   - **여전히 정하지 않는 것.** 며칠·몇 MB·콜드 스토리지 대상. 배포 파라미터이고 실측 회전율이
     없다(`0003 §8-5`가 같은 이유로 미룬 것과 같은 판단).
7. **유량 제한의 구체값.** §1.5가 `429`를 정의했지만 한도를 정하지 않았다. 배포 파라미터로
   두되, §2.3의 "단건 write-through가 1급"을 무력화하는 값이면 안 된다는 제약만 있다.
8. **`maxEventBytes`의 실제 값.** §1.3은 하한 1 MiB만 정했다. 실제 값은 배포가 정하고
   `413`의 `details`로 알린다. 별도 discovery 라우트를 두지 않은 것은 전송 평면 라우트를
   셋으로 유지하기 위해서다 — 라우트가 늘어야 할 만큼 불편해지면 그때 재검토한다.
9. **구 인스턴스 통합** (0001 §4.3). 이 스펙은 구 relay와 와이어 호환이 아니다
   (라우트 이름·커서 의미·내구성 계약이 다르다). 통합 시점과 방식은 미정.
10. **mori #115 본문과의 어긋남 1건 (클라이언트 쪽).** #115는 커밋되는 정체성 파일에
    "hub 프로젝트 ID·URL"을 담는다고 적었는데, 0001 §2.5는 **프로젝트 ID만** 담고 hub
    주소·자격증명은 절대 담지 않는다고 못박았다(악의적 fork가 기억을 남의 hub로 보내는 것을
    막기 위해). 이 스펙은 0001을 따라 베이스 URL을 **런처 주입**으로 둔다(§1.1). #115 본문이
    0001보다 앞선 기록이므로 그쪽이 낡은 것으로 보이지만, **클라이언트 쪽 변경은 이 문서의
    범위가 아니므로** 고치지 않고 남긴다 — mori #115 1단계에서 확인이 필요하다.
11. **출처 값을 응답에 싣는가.** §1.6은 **기록만** 하기로 했다. 실어야 할 이유(클라이언트 쪽
    귀속 표시 등)가 생기면 여는데, 그때 **함께** 답해야 하는 것은 *"출처를 볼 자격이 누구에게
    있는가"* 다 — 같은 로그를 스코프에 든 작업공간이 다른 작업공간의 `workspaceId`·`tokenId`를
    보아도 되는지는 정해져 있지 않다. 지금 정하지 않는 이유: 이 축의 소비자가 아직 서버 자신뿐
    이라 노출 없이도 막히는 것이 없고, 넓히는 방향이 거두는 방향보다 훨씬 싸다(§1.6).
    - **[2026-08-07] 미루기의 근거 하나가 만료됐다 — 항목은 여전히 열려 있다.** §8-12가
      되돌림을 **클라이언트가 읽는 무효 선언**으로 닫으면서, 소비자가 *"이 무효 선언을 정당한
      주체가 냈는가"* 를 가려야 하는 자리가 생겼다
      (`selective-removal-and-retention-adjudication.md` §Q1.3). 그 판단의 유일한 사칭 불가
      재료가 §1.6의 출처 값인데 응답에 실리지 않으므로, **이 축의 소비자가 서버 자신뿐이라는
      전제는 더 이상 참이 아니다.** 위의 재검토 조건(*"실어야 할 이유가 생기면"*)이 충족됐다.
      함께 답해야 하는 질문 — *"출처를 볼 자격이 누구에게 있는가"* — 은 그대로 남는다. 이
      항목을 여는 조각은 같은 산정 §Q5-T2이고, **실질적 시한은 되돌림이 실제로 쓰이기 전**이다:
      노출 없이 되돌림을 돌리면 사칭 가능한 무효 선언이 쌓이고 로그는 append-only라 소급해
      고칠 수 없다(§1.6).
12. **[닫힘 2026-08-07] 출처 축으로 특정한 집합에 대해 서버가 무엇을 할 수 있는가.** §1.6은
    **특정**까지만 세운다 — *"작업공간 W가 기간 Y에 이 로그에 남긴 것"* 을 정확히 집어낼 수
    있게 하는 데서 멈춘다. 그 집합을 어떻게 할 것인가(읽기 경로 필터 / 클라이언트가 읽는 무효
    선언 / 보존과 함께 실제 삭제)는 §1.4의 삭제 금지와 §8-6(보존)이 함께 열려야 정해진다.
    읽기 경로 필터는 §3.2가 세운 **조용한 누락 금지**와 정면으로 부딪히므로 그 셋을 따로 고를
    수 없다.
    - **받은 자리: §1.4 「되돌림의 자리」** + `selective-removal-and-retention-adjudication.md`
      §Q1·§Q4. 셋을 합동으로 받은 결과 **클라이언트가 읽는 무효 선언**이 채택됐다 — §1.4가
      *"retract는 payload 안의 클라이언트 개념"* 으로 이미 그렇게 적고 있었고, 이 선택만이
      전송 평면에 새 조항을 만들지 않는다.
    - **읽기 경로 필터**는 §3.2의 조용한 누락 금지(MUST NOT)를 깎아야 하고, 필터의 값어치가
      *"소비자가 몰라도 된다"* 에 전부 있으므로 갭을 알리도록 고치면 무효 선언으로 내려온다.
      **보존과 함께 실제 삭제**는 §1.4의 MUST NOT을 뒤집고 §5 표 3행·§6 표 3.4행을 함께
      무너뜨려 `0001 §1` 계승 불변식 3의 개정으로 올라간다 — 이 문서가 스스로 할 수 없다.
    - **남는 잔여물 둘** (이 항목이 닫히면서 다른 자리로 넘어간 것): 되돌림이 **advisory**라
      "선별 제거"가 문자 그대로 만족되지는 않는다는 것(§1.4), 그리고 무효 선언의 주체 검증이
      §8-11에 걸린다는 것(위 §8-11의 2026-08-07 주석).
